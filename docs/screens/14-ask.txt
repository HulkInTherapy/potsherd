potsherd ask "what did we decide about prepared statements behind the pooler?"

ANSWER
  Because transaction pooling drops session state, server-side prepared
  statements don't survive a transaction boundary. [1] The decision was to
  disable prepared statement caching on the client by setting
  statement_cache_size=0. [2] This was verified with a test: it failed against
  the old client config with a "prepared statement already exists" error, and
  passed once the cache was disabled. [3]
