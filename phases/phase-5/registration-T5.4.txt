1. JOB 2, PART TWO — THE SILENCE ITSELF, AND WHY IT MOVED TO SessionStart
================================================================================

The brief asked whether the hook could surface a one-line `systemMessage` the
first time a download happens. It cannot — not on `SessionEnd`.

  code.claude.com/docs/en/hooks.md, SessionEnd, verbatim:
    "Discards universal fields: Yes - `systemMessage` is discarded"
    "SessionEnd hooks have no decision control. They can only produce side
     effects through `terminalSequence`. Exit codes and `systemMessage` are
     ignored."

So the announcement was moved to where it can be heard AND where it is more
useful — `SessionStart`, BEFORE the download rather than during it.

  SessionStart, same page, verbatim:
    "`systemMessage`: A message shown to the user. On `UserPromptSubmit`,
     `UserPromptExpansion`, and `SessionStart`, Claude sees it as context."

WHAT WAS ADDED. One clause in the existing SessionStart rescue hook, after the
binary resolution and before the detached `rescue`:

    MD="${POTSHERD_DIR:-$HOME/.potsherd}/models"
    [ -n "$(find "$MD/Xenova/bge-small-en-v1.5/onnx" \
            -name '*.onnx' -size +1000k 2>/dev/null | head -1)" ] \
      || printf '{…"systemMessage":"…%s…"}\n' "$MD"

It is a pure-shell restatement of `isModelCached()` in
`packages/core/src/embeddings.ts` — same directory, same ">1 MB `.onnx`" test —
so it needs no Node startup. It fires only while the model is absent, which in
practice means once, and it names the size, the model id, the target directory
and the way to opt out.

  MEASURED COST                  20 runs      per run
    probe alone, model absent      84 ms       4.2 ms
    probe alone, model cached      77 ms       3.9 ms

  Against T5.3's measured 6.5 – 10.5 ms SessionStart, that is ~4 ms added on
  every start and no change to what the hook does. Not slow, and not noisy:
  it emits nothing once the model is on disk.

VERIFIED BY EXECUTION, not by reading. The command was extracted from
`hooks.json` and run under a throwaway `HOME` in all three states:

    model absent   -> valid JSON, hookEventName SessionStart, 509-char
                      systemMessage, correct models directory interpolated
    stub .onnx     -> still warns (the >1 MB test is what makes this correct;
                      a partial download must not read as cached)
    model cached   -> EMPTY. silent.

`hooks.json` was rewritten programmatically rather than by hand, so the
four-level quoting (JSON file -> shell string -> printf format -> JSON payload)
is machine-generated. The diff is one line.

THE ONE THING NOT FIXED, AND IT IS NOT MINE TO FIX. This warning does not cover
a user who runs `potsherd index --quiet` or `--json` by hand from a script; for
them the download is still silent, and the reworded receipt now says so
explicitly rather than implying otherwise.

================================================================================

T5.3 §3 is the warning: `claude plugin validate` passed a manifest that Claude
Code refused to load, because declaring `"hooks": "./hooks/hooks.json"`
duplicated a conventionally-discovered file and the WHOLE PLUGIN was dropped.
The brief said to assume codex has its own version of that trap and to prefer
declaring less.

Codex has the same three conventions — and, read in source, not the same trap:

  codex-rs/core-plugins/src/loader.rs
      const DEFAULT_HOOKS_CONFIG_FILE: &str = "hooks/hooks.json";
      const DEFAULT_MCP_CONFIG_FILE:   &str = ".mcp.json";
      const DEFAULT_SKILLS_DIR_NAME:   &str = "skills";

      match &manifest_paths.hooks {
          Some(PluginManifestHooks::Paths(paths)) => { … }
          …
          None => {
              let default_path = plugin_root.join(DEFAULT_HOOKS_CONFIG_FILE);
              if default_path.as_path().is_file() { … }
          }
      }

The declared key and the conventional probe are MUTUALLY EXCLUSIVE match arms.
Declare it and the default branch never runs; omit it and the default path is
probed. So in codex, unlike Claude Code, declaring is survivable.

DECISION: declare nothing anyway. `plugin.json` carries no `skills`, no
`mcpServers`, no `hooks`, no `apps`, no `commands` — only identity and
`interface`. The files sit at the conventional paths. Both routes work; the one
that cannot double-load was chosen, and it costs nothing.

Corroborated on disk: every OpenAI-shipped manifest under
`~/.codex/plugins/cache/` (`visualize`, `browser`, `slack`, `documents`, `pdf`,
`presentations`, `spreadsheets`, `template-creator`) declares `"skills"`
explicitly and NONE declares `mcpServers` or `hooks`.

A second rule that would have bitten a declared path: every path value must
begin with `./`, and `resolve_manifest_path` drops the field with only a
`tracing::warn!` if it does not — no error, no non-zero exit. Another silent
one. This manifest declares no paths, so it cannot trip it.

7. JOB 1 — THE ONE DESIGN FORCED BY CODEX, AND THE RISK IN IT
================================================================================

** ${PLUGIN_ROOT} IS NOT INTERPOLATED INTO AN MCP SERVER'S command/args. **

Claude Code's `.mcp.json` interpolates `${CLAUDE_PLUGIN_ROOT}` (T5.3 §0 verified
it). Codex does not: `codex-rs/codex-mcp/src/plugin_config.rs` contains no
placeholder substitution at all. What it does instead:

    if let PluginMcpSource::Host { root } = source
        && let Some(JsonValue::String(cwd)) = object.get("cwd")
        && !Path::new(cwd).is_absolute()
    {
        object.insert("cwd".to_string(),
            JsonValue::String(root.join(cwd).display().to_string()));
    }

A relative `cwd` is joined with the plugin root; `command` and `args` are passed
through untouched. So the only way to reach a file near the plugin without
interpolation is to pin `cwd` and let the child resolve a relative argument:

    { "type": "stdio", "command": "node",
      "args": ["../../packages/mcp/dist/index.js"], "cwd": "." }

`"type": "stdio"` is accepted — `plugin_config.rs` explicitly matches
`"http" | "streamable_http" | "streamable-http" | "stdio"`. The file may use a
`{"mcpServers": {…}}` wrapper or a bare map; `PluginMcpFile` is an untagged enum
over both. The wrapper is used, matching the claude-code plugin.

  THE RISK, STATED PLAINLY: pinning `cwd` means the MCP server does NOT inherit
  the user's project directory. `graft` writes its brief to `./.potsherd/
  graft-<id>.md` in the working directory, so on codex it would land beside the
  plugin instead of beside the user's code. This is UNTESTED — `packages/mcp`
  does not exist on this commit — and it is written up in the codex README as
  the thing to check first. If codex turns out to interpolate `${PLUGIN_ROOT}`
  after all, an interpolated absolute path is strictly better and the fix is a
  two-line edit.

ENV VARS FOR HOOK COMMANDS, verbatim from
codex-rs/hooks/src/engine/discovery.rs:

    env.insert("PLUGIN_ROOT".to_string(), plugin_root_value.clone());
    // For OOTB compat with existing plugins that use this env var.
    env.insert("CLAUDE_PLUGIN_ROOT".to_string(), plugin_root_value);
    env.insert("PLUGIN_DATA".to_string(), plugin_data_root_value.clone());
    // For OOTB compat with existing plugins that use this env var.
    env.insert("CLAUDE_PLUGIN_DATA".to_string(), plugin_data_root_value);

There is NO `CODEX_PROJECT_DIR` and no `CODEX_PLUGIN_ROOT`. The project
directory arrives as `cwd` on the hook's stdin. The hooks here take
`${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT:-}}` so either name works.

Note the shape of the SessionEnd session id is the same as Claude Code's —
`session_id` on stdin — so T5.3's `sed` extraction was reused unchanged, and it
is the id that `index --session` resolves (§6).
