** THE ONE THAT WOULD HAVE FAILED SILENTLY **

  The phase file specifies `index --session $CLAUDE_SESSION_ID`.
  `CLAUDE_SESSION_ID` IS NOT A HOOK ENVIRONMENT VARIABLE. It is not in the
  documented list and never has been. Written as specified, the hook would
  expand it to the empty string and index nothing, forever, with exit 0 — the
  exact failure phase 0 legislated against.

  The session id is available only on the hook's STDIN, as `session_id` in the
  event JSON. The SessionEnd hook therefore reads stdin:

      ID=$(sed -n 's/.*"session_id"[[:space:]]*:[[:space:]]*"\([^"]*\)".*/\1/p' \
           | head -1); [ -n "$ID" ] || exit 0

  Tested against pretty-printed event JSON, which is what arrives; the pattern
  is line-based and works for compact JSON too. If no id is found it exits 0
  having done nothing, which is correct — there is nothing to index.

  ACTION FOR THE ORCHESTRATOR: `03 §9` and phase-5's deliverable 2 both still
  say `$CLAUDE_SESSION_ID`. That line is wrong and should be corrected in the
  plan folder per `00-README.md` rule 5.

2. MARKETPLACE PATH — .claude-plugin/marketplace.json AT THE REPOSITORY ROOT
================================================================================

The brief allowed either location and asked which and why. It is the repo root,
and it is NOT under plugins/claude-code/.

  plugin-marketplaces.md, verbatim:
    "Create `.claude-plugin/marketplace.json` in your repository root."
    "Paths resolve relative to the marketplace root, which is the directory
     containing `.claude-plugin/`. In the example above, `./plugins/my-plugin`
     points to `<repo>/plugins/my-plugin`, even though `marketplace.json` lives
     at `<repo>/.claude-plugin/marketplace.json`. Don't use `../` to reference
     paths outside the marketplace root."

`/plugin marketplace add HulkInTherapy/potsherd` clones the repo and reads its
ROOT. A marketplace.json under plugins/claude-code/ would never be found, and
because sources may not use `../`, it could not point back at the plugin from
there either. Hence root, with `"source": "./plugins/claude-code"`.

Marketplace name is `potsherd`, so installs read `potsherd@potsherd`. Not one
of the reserved names.

6. bin/potsherd — REASSIGNED MID-TASK, AND WHAT IT CANNOT DO
================================================================================

T5.2 flagged that `bin/**` was in nobody's WAVE column while its skills route
all fifteen verbs through `${CLAUDE_PLUGIN_ROOT}/bin/potsherd`; the orchestrator
reassigned it here. Delivered, mode 0755.

RESOLUTION ORDER — deliberately not phase 0's:

  1. ${CLAUDE_PLUGIN_ROOT}/dist/potsherd.js               vendored
  2. ${CLAUDE_PLUGIN_ROOT}/../../packages/cli/dist/…      the checkout
  3. potsherd on PATH                                     global install
  4. nothing -> names all three paths, exits 127

`resolve-bin.ts` prefers PATH because it writes into the user's settings.json,
where a portable spelling survives upgrades. A plugin is the opposite case: it
carries a version and speaks a pinned archive format, so a stale global must
not answer for it. Not hypothetical here — PATH holds 0.1.0, the checkout
holds 0.4.0.

PROVEN, as asked:

    $ plugins/claude-code/bin/potsherd --version
    0.4.0                     (PATH's `potsherd --version` prints 0.1.0)

    $ plugins/claude-code/bin/potsherd doctor
    potsherd doctor · potsherd 0.4.0 · node v24.9.0
      database                schema v8 of v8
      vectors            56   sqlite-vec v0.1.9 · bge-small, 384-d
      fatal parse errors  0   none
    EXIT=0

    $ <from a marketplace install, clean PATH>
    potsherd: this plugin has no potsherd to run, so nothing was done.
    Looked in three places: ... EXIT=127

WHAT IT CANNOT DO, AND WHAT IS NEEDED — T5.6's call, not made here.

T5.2's measured constraint is confirmed: `packages/cli/dist/potsherd.js` is one
602 KB esbuild file but is NOT self-contained — it still resolves
`better-sqlite3` and `sqlite-vec` through `createRequire` at runtime, so it
needs a `node_modules` beside it with both built for the host platform.

A marketplace install is a git clone. This repo gitignores `dist/`, and a clone
has no `node_modules`. Verified end to end: after a real
`claude plugin install potsherd@potsherd`, the installed shim skipped steps 1
and 2 and answered `0.1.0` from PATH.

  SO, TODAY: a marketplace install of this plugin REQUIRES `npm i -g potsherd`.
  Steps 1 and 2 are dead on that path.

Making step 1 live needs a packaging change to `packages/cli` — RESERVED, and
T5.1 and T5.5 are both live in there — so it is reported, not done. One of:
  (i)  vendor dist/ + a per-platform node_modules into the plugin (large, and
       needs a build step in the release pipeline), or
  (ii) keep `npm i -g potsherd` as a declared prerequisite (small; what the
       README documents today), or
  (iii) make the marketplace entry `"source": {"source": "npm", ...}` so the
       published package IS the plugin.
The same constraint applies to `.mcp.json`, which points at
`${CLAUDE_PLUGIN_ROOT}/../../packages/mcp/dist/index.js` — the path the phase
file's own verification command uses. It works from a built checkout and not
from a marketplace clone, for exactly the same reason.

7. CLI FLAGS THE SPEC ASKED FOR THAT DO NOT EXIST
================================================================================

Checked each of the three named in the brief against packages/cli/src/index.ts.

  --quiet         EXISTS on rescue, index, card.        used as specified.
  --no-settings   EXISTS on rescue.                     used as specified.
  --background    DOES NOT EXIST on rescue, or anywhere.

No flag was added. The hooks detach in the shell instead:

    (trap '' HUP; "$P" ${A:+"$A"} rescue --yes --quiet --no-settings) \
      </dev/null >/dev/null 2>&1 & exit 0

`trap '' HUP` in a subshell rather than `nohup`, so the same line works when
`nohup` is absent; all three stdio streams are closed so Claude Code's pipe
sees EOF and does not wait. Measured effect in §1: 7.0 ms to return, 1.75 s of
work afterwards.

ALSO NOT PRESENT, and worked around rather than added:

  `index` has no `--card`. The phase file wants a card on SessionEnd only when
  `cardOnEnd` is set, so the hook greps ~/.potsherd/config.json itself and
  chains `card "$ID" --quiet --yes` after `index`. Nothing in core reads
  `cardOnEnd` — `paths.ts` knows where config.json is and nothing parses it.
  If a later task gives config.json a real reader, this grep should become a
  call to it.

  There is no `brief` verb. The optional SessionStart injection is assembled
  from two `potsherd ls` calls (`--since 7d` to decide whether the project is
  cold, then `--limit 5` for the titles) and capped at 4,800 chars ~= 1,200
  tokens. It is gated on `briefOnStart` in the same config.json and costs
  ~25 ms to decline. Measured output on a cold project: 448 chars, ~112 tokens.

8. A PRIVACY-RECEIPT GAP THIS HOOK CREATES — ORCHESTRATOR DECISION
================================================================================

`doctor --privacy` says, verbatim:

    no other network, except the one-off embedding-model download that
    `potsherd index` announces before it starts and `--no-embed` skips.

"announces before it starts" is true when a human runs `index`. It is NOT true
on the hook path: SessionEnd runs `index --session <id> --quiet`, detached, so
the announcement is suppressed and nothing is shown.

MEASURED: one SessionEnd hook firing produced 33 MB in
`<potsherd-dir>/models/Xenova/bge-small-en-v1.5/` — a network fetch the user
neither typed nor saw.

Not narrowed to fit. Adding `--no-embed` to the hook would kill vector search
on every newly-ended session, and the brief is explicit that shrinking the work
to hit a target is the wrong move. The README discloses it in plain text. The
real options are a product decision:
  (a) leave it, disclosed in the README only;
  (b) reword the receipt so the sentence is true on both paths (packages/core,
      and the receipt is CI-guarded, so it is a deliberate change);
  (c) have the plugin's first run fetch the model once, visibly, at install.

The published receipt itself is UNCHANGED by this task — nothing under
packages/ was touched, so the CI privacy guard has nothing to catch.
