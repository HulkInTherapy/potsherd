2. THE DESIGN, VERIFIED RATHER THAN FOLLOWED
================================================================================

2a. `--readers-out` MAKES ZERO MODEL CALLS **BY CONSTRUCTION** — CONFIRMED
--------------------------------------------------------------------------------
T5.2 asked for this to be checked against the current `ask.ts` and stated with
line references. It is true, and here they are:

  packages/core/src/ask.ts:1047
      const ownReader = o.readerFn ? null : o.readerLlm ?? openLlm(…);
    → supplying a `readerFn` means **no reader backend is constructed at all**.

  packages/core/src/ask.ts:1104
      if (answered.length === 0) {
        return base({ refused: strict, refusal: strict ? 'no-answer' : null });
      }
    → every recorded reader reports `found: false`, so this returns …

  packages/core/src/ask.ts:1116
      const ownSynth = o.llm ?? openLlm(o.model ?? ASK_MODEL, budget, o);
    → … before the only line in the function that opens the synthesizer's
      backend. `filterAnswer` (1134) and `tryOpenThreads` are both below it.

There is no branch to get wrong and no flag to forget: on this path the
function never evaluates an expression that could construct a backend. Proved
in the tests with a `Throwing` transport passed as *both* `llm` and
`readerLlm`, asserting `transport.sent` is empty and `spend.calls` is 0.

A consequence worth naming: `--readers-out` therefore does **not** require a
backend to exist. `detectBackend` is skipped for it in the CLI. Demanding a
`claude` binary for a run that structurally cannot call a model would be the
CLI saying something untrue about it, and it would put a binary between a
skill and the one path that needs no model. Verified on the live binary with
`POTSHERD_LLM_BACKEND=none`: a normal `ask` exits 1 with "no way to reach a
model", `--readers-out` writes its file and exits 0.

2b. `--readers-in` CANNOT SKIP THE SHORTLIST, AND MUST NOT
--------------------------------------------------------------------------------
T5.2 §2 says `--readers-in` "skips shortlist and readers". It skips the
readers. The shortlist has to run, and that is not a limitation:

  - `filterAnswer(proposed.answer, proposed.evidence, targets)` checks every
    quote against the **live transcript bytes** at the `(sessionId, seq)` it
    names. `targets` is the shortlist. Without it there is nothing to check
    against, and the guarantee becomes something the file asserts about
    itself — which is exactly the property the flags exist to restore.
  - `AskResult.matching` and the render's "n of m sessions read" come from the
    shortlist too.

So a replay runs `recall` once more. On the fixture that is ~100 ms; no model,
no network beyond the local embedding pass, which `--vectors off` skips
entirely.

2c. THE REPLAY VALIDATES **BEFORE** IT SPENDS — TWO PASSES
--------------------------------------------------------------------------------
Since the shortlist re-runs, the recorded ids and the live shortlist can
disagree. Learning that from inside `readerFn` is too late: `ask()` treats a
thrown reader as "this session contributed nothing" (a deliberate phase-4
ruling) and carries on to pay for the synthesizer. So `--readers-in` runs the
`--readers-out` recorder first — zero model calls by the same construction as
2a — takes the live shortlist from it, checks the file, and only then replays.

Reusing the recorder rather than re-deriving the shortlist in the CLI is
deliberate. `ask()`'s `recall` call is tuned with measured reasons in its own
comments (candidate depth pinned to `find --limit k`, vectors defaulted on). A
second copy of that call in `commands/ask.ts` would drift, and the drift would
present as a stale file.

2d. THE RULING ON A PARTIAL MATCH: **ANY DIFFERENCE IS AN ERROR**
--------------------------------------------------------------------------------
The tempting alternative is to answer from the overlap. It is wrong in a way
the user cannot see. `searched` and `matching` are printed as "n of m sessions
read", and on a partial replay those would be the *live* shortlist's numbers
over a file that covers less than it. The answer would read as a full sweep
while a session the shortlist ranked into the top k contributed nothing — and
`filterAnswer` cannot see that, because it checks the quotes it is given and
has no view of the ones nobody produced. That is "silently answer from a stale
file", arrived at one session at a time.

The error names both directions, because they fail differently and only one is
dangerous:

  - in the shortlist, not in the file  → a hole in coverage. The real failure.
  - in the file, not in the shortlist  → merely unused, but it means the index
                                          moved, so the first case is likely too.

The cause is always the same (the index changed between record and replay) and
the fix is always one command, which the error prints.


================================================================================
3. THE FILE FORMAT
================================================================================

One envelope for both directions, on purpose: a skill reads the file, fans its
own Agent readers out over `targets`, adds `outputs`, and hands **the same
file** back. Transcribing six session ids from one shape into another is a
step that can go wrong silently.

  {
    "kind": "potsherd.ask.readers",     // discriminator; wrong kind → refuse
    "version": 1,                        // envelope version; wrong → refuse
    "potsherd": "0.4.0",                 // the binary that wrote it (informational)
    "question": "…",                     // redacted as llm.ts would redact it
    "k": 6,
    "sessionIds": ["…"],                 // the shortlist, in shortlist order
    "targets": [ AskReaderInput, … ],    // T4.4's object, verbatim
    "outputs": [ { "sessionId": "…", ...AskReaderOutput }, … ]   // added by the reader
  }

Mismatch detection, in the order it runs, all of it before any model call:

  kind ≠ potsherd.ask.readers   → refuse   ("is not a reader file")
  version ≠ 1                   → refuse   ("a v99 reader file and this potsherd reads v1")
  no/blank question             → refuse
  question ≠ this question      → refuse   ← "a file recorded against a different
                                             question must not be replayable"
  k ≠ this run's k              → refuse   (a different k is a different shortlist)
  no "outputs"                  → refuse   ("a recording nobody has read yet")
  malformed output entry        → refuse   (missing sessionId / non-boolean found /
                                            non-integer seq / non-string text)
  sessionIds ≠ live shortlist   → refuse   (§2d)
  outputs' ids ≠ live shortlist → refuse   (§2d)

**Filters are not recorded, and do not need to be.** `--project`, `--since`,
`--tag` and the rest change *which sessions are shortlisted*, so any filter
difference between the recording and the replay shows up as a session-id set
difference and is caught by the last two checks. Recording the filter objects
would add a second, weaker copy of a check that already exists.

`--readers-out` records at `concurrency: 1`, so the recording order is the
shortlist order and two recordings over an unchanged index are byte-identical.
A test asserts it. The file ends with a newline.

5. REDACTION — THE RULING, ANSWERED
================================================================================

**The reader inputs `readerFn` receives are already redacted, in exactly the
state a model would have been sent them.** This is not an assumption:

  - Redaction is L2. `packages/core/src/index.ts:74` — *"redaction. Runs
    before anything is written to the index (`03` §5)"*. `ingest.ts` elides
    binary payloads and then runs `redactExchange` on every exchange before a
    row is inserted. The store is masked at rest.
  - `AskReaderInput.excerpts` is built by `excerptText(t.units)` from those
    rows. `ask.ts:255` says so: *"already capped and redacted at rest"*.
  - `llm.ts`'s outgoing pass is `redactOutgoing = redact(elideBinary(text))`,
    and its own comment (llm.ts:1879-1882) says it is *"identical to the
    ingest path, deliberately: what a model sees and what the index holds are
    the same text"*.

So there was no finding to escalate. It is still belt-and-braces'd, because
this flag writes to a path the user names rather than to a model:
`--readers-out` re-runs `redactOutgoing` over each `excerpts` and over the
`question` before writing. Two tests hold it:

  - on the ordinary fixture, `redactOutgoing(excerpts).hits === 0` and the
    text is unchanged — i.e. the second pass is a **no-op today**, asserted
    rather than assumed, so a future divergence between the two rule sets
    fails a test instead of leaking.
  - a credential seeded straight into the index (past ingest, the only way it
    could be there) does not appear in the written file; a `‹redacted:aws:…›`
    mask does.

Running it also keeps the two paths *identical*: a native Agent reader quoting
this text quotes what an SDK reader would have been shown, so `filterAnswer`
behaves the same on both.

There is still no `--no-redact` and these flags do not become one.
