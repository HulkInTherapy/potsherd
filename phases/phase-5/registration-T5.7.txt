1. THE RULE I CHOSE FOR "REAL CONTENT", AND WHY
================================================================================

The brief said this is a judgement call and asked for the reasoning rather than
a heuristic. The rule is written in full at the top of scripts/check-privacy.py
and repeated in its failure output, so a red run teaches it. In short:

A committed file carries REAL-CORPUS CONTENT when it reproduces, or lets a
reader reconstruct, something that was inside a live AI transcript or the
private working tree that transcript ran in. Three families:

  1. TRANSCRIPT PROSE — what a human typed, what an agent replied or reasoned,
     verbatim or near-verbatim. And the subject matter of it: a topic that is in
     this repo only because it was in somebody's real sessions is the same leak
     in fewer words. The `potsherd find "<topic>"` example in `--help` is a leak
     for exactly the reason the pasted user message was.

  2. CORPUS IDENTITY — a session, thread or composer uuid that indexes a live
     transcript, and a session title.

  3. THE PRIVATE TREE — a home path or project slug naming a directory that is
     NOT this repository, plus the file names and contents inside it.

Family (3) is the part worth defending, because it is where "it's only a path"
gets said. A project directory name is a fact about somebody's private life:
two of the names in REAL_PROJECT_NAMES say what a person was studying and what
they were building. And the slug is the join key back to the transcript —
`-Users-<name>-<project>` is literally how Claude Code indexes it. So a project
name is a violation on its own, with no prose attached.

Three things that look like violations and are NOT, because banning them would
cost the repo something it needs:

  a. THIS REPO'S OWN CHECKOUT PATH. It names no private work. It is in the
     banner of every pasted `pnpm test` and `vitest` run, and the unedited
     banner is what makes a pasted run evidence instead of a claim. Editing it
     would degrade the artefact to protect nothing.

  b. A KEPT `--potsherd-dir` CITED AS EVIDENCE. plans/00-README.md's ground
     rules REQUIRE it: "a real-corpus run is cited by its kept `--potsherd-dir`
     and its numbers". The path is mandated. What must not follow it is the
     transcript-derived prose. Re-examinable does not mean published, and the
     citation is the re-examinable half.

  c. OBVIOUSLY SYNTHETIC PLACEHOLDERS AND THE DEMO CORPUS'S OWN IDS.
     `/path/to/project`, `/Users/example`, `00000000-…`, and evals/fixture/,
     tests/fixtures/, docs/screens/, all generated from a seeded PRNG.

This is why the guard is not `grep -r /Users/`. That heuristic would demand
scrubbing the very citations the ground rules ask for, and a guard that asks you
to break a rule is a guard people turn off. `is_private_home()` decides per
token instead, against one short OWN_TREE_ROOTS list with the reason beside it.

A MATERIALITY CLAUSE inside family (1), which is the one place I let real text
stand. `"hello"`, `"yo"` and `"hello what is this project about??"` are real
user messages, kept in PHASE-1-SCOUT.md. They identify no person, no project and
no subject, and they are load-bearing: they are what proves pi's user prompts
run 2–232 chars and that its `user` role is never overloaded. Same for the one
generic thinking block ("The user is asking about the project in the current
working directory"). The test is not "did a human write it" but "does it tell a
reader something about a person, a project, or private work". Where the answer
was yes, it went.

TWO THINGS I DECIDED TO KEEP AND WANT ON THE RECORD, so a later reviewer can
overrule me rather than rediscover them:

  - `"timezone":"Asia/Kolkata"` and the `(UTC+5:30)` stamps in PHASE-1-SCOUT.md.
    A timezone is coarse — it is shared with a fifth of the planet — and it is
    structurally load-bearing here: the section's warning that "the filename
    timestamp is LOCAL wall-clock, every timestamp inside is UTC, here they
    differ by 5h30m" is built on it. Cheap to change if you disagree; say so.

  - opaque provider-side response ids: `msg_08ae2935…`, `rs_08ae2935…`,
    `ctc_08ae2935…`, `call_hfAHQ9CKZlI6yJ7TTpRAAmRK`, and pi's 8-hex DAG ids
    (two of them were named here in the clear; both are withheld as of T8.H,
    22 aug 2026). These are real, but they link to no person and
    no machine, no guard can tell them from synthetic ones, and pi's ids carry
    the parent/child chain the DAG section exists to explain. Every uuid in that
    file is now one I minted; these are not uuids.

5. THE HONEST LIMIT
================================================================================

No regex recognises prose. Family (1) is caught only by its known vocabulary and
family (2) — a live session uuid — not at all, because nothing distinguishes a
real uuid from a synthetic one by looking at it. This guard is a FLOOR, not a
ceiling: green means the repo carries no leak we have already seen, not that it
is clean. That sentence is in the script's header and in its failure output on
purpose, so nobody reads a green run as a clearance.

One known blind spot found while writing it: the home-path rule matches
`/Users/x/y` but not an escaped form like a regex literal `/\/Users\/x/`, which
is how tests/adapters/cursor.test.ts spells it. That file is allowlisted anyway,
but a future file could hide a path the same way.

The thing the guard does buy: PHASE-1-SCOUT.md was scrubbed twice, and the
second pass (this one) found session-id fragments the first had missed, because
between the two passes nothing was watching. From f806b63 something is.

T8.H, 22 aug 2026 — AMENDMENT to the ruling above.

The ruling "these are real, but they link to no person and no machine" was
followed, and it was wrong on its own terms. `no guard can tell them from
synthetic ones` is a statement about the guard, not about the ids: the ids
are real record ids inside real `~/.pi` transcripts, in a public repository,
and this is the same shape as the `thinking` block `docs/upstream/PHASE-1-
SCOUT.md` published for six phases — one level down the record tree.

`scripts/check-privacy.py` now enumerates every id-shaped token in tracked
text and asks which source in the repository accounts for it, so the second
half of the ruling no longer holds either: a guard CAN now tell, not by
recognising a real id, but by refusing to accept an unexplained one.

The two ids named above and the seven in `PHASE-1-SCOUT.md`'s DAG table and
chain example are substituted with synthetic ids of the same shape. Every
number, every chain and every finding in both files is unchanged. The
provider-side `msg_`/`rs_`/`ctc_`/`call_` ids in the list above are NOT
touched: they are opaque provider response handles, they are not id-shaped
in this guard's terms, and the rest of that ruling stands.
