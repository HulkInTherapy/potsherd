## 0. The claim this project carried for five phases, and what it actually costs

Phases 5 through 9 all state, in one form or another, *"X is not installed here
and cannot be"*, and label both the transport and the plugin
`unverified — documentation only` on that basis. **Nobody ever ran `npm view`.**

```
$ npm view @openai/codex version   ;# → 0.149.0
$ npm view @google/gemini-cli version   ;# → 0.56.0
$ npm view opencode-ai version   ;# → 1.18.21
$ npm view @github/copilot version   ;# → 1.0.80

$ npm install @google/gemini-cli@0.56.0 opencode-ai@1.18.21 @github/copilot@1.0.80
added 35 packages in 33s
```

**All four install. Three of them in thirty-three seconds, together.** Rule 8
says *verify a flag exists before documenting it*; its mirror is *verify a tool
is really unavailable before labelling it so*, and this project had never once
applied the mirror. Four adapters, one transport and one plugin were labelled on
an assumption that took 33 seconds to falsify.

Of the four, **one answered without credentials of ours** (opencode, through its
bundled provider) and three refused at auth. Three of the four had *never been
run at all* on this machine before today, and the moment they were, **three of
the four adapters turned out to be reading the wrong thing.**

#### F1 — `event_msg/user_message` no longer exists

`parser/codex.ts:265` `collectHumanPrompts()` scans for
`type:"event_msg"` + `payload.type === "user_message"`. **codex 0.149.0 emits
none.** It emits, for the same turn:

```json
{"type":"event_msg","payload":{"type":"item_completed","thread_id":"…","turn_id":"…",
  "item":{"type":"UserMessage","id":"…","content":[{"type":"text","text":"say hello"}]}}}
```

So `humanPrompts` comes back empty, the guard at `parser/codex.ts:184`
(`if (humanPrompts.size > 0 && !humanPrompts.has(normalise(text))) continue;`)
never engages, and **every** `response_item/message` with `role:"user"` starts an
exchange — including `<environment_context>`. The file header calls this the
"no `event_msg` records at all" degrade; it is firing on a rollout with three of
them. The guard tests for the wrong thing: it asks *"did I find any human
prompts?"* when the question is *"does this file use the stream I know how to
read?"*.

Reproduced as a unit test: `tests/adapters/codex.test.ts`, describe block
*"a real codex-cli 0.149.0 rollout (T10.12)"*, `FINDING F1`.

**RECOMMENDED EDIT — `packages/core/src/parser/codex.ts`, `collectHumanPrompts`.**
Additive; cannot change what an already-readable rollout parses to, because the
2026-07 format has no `item_completed` records:

```ts
    if (!isRecord(payload)) continue;
    if (payload.type === 'user_message' && typeof payload.message === 'string') {
      out.add(normalise(payload.message));
      continue;
    }
    // codex-cli 0.149.0 renamed this event. Same ground truth, new envelope.
    if (payload.type === 'item_completed' && isRecord(payload.item)
        && payload.item.type === 'UserMessage') {
      const text = extractTextFromContent(payload.item.content);
      if (text.trim()) out.add(normalise(text));
    }
```

Do **not** also change the `humanPrompts.size > 0` guard to something stricter
in the same edit: with the above, a 0.149.0 rollout produces a non-empty set and
the existing guard is correct again, and a genuinely event-less rollout still
degrades to upstream's behaviour, which is the documented contract.

#### F2 — `session_index.jsonl` is gone

`adapters/codex.ts:32` calls it *"the ONLY title source"*.

```

0.149.0 keeps thread metadata in **`$CODEX_HOME/state_5.sqlite`**:

<uuid>|say hello|say hello|0.149.0

`title`, `first_user_message` and `preview` are all `say hello`. **The correct

**RECOMMENDED EDIT — `packages/core/src/adapters/codex.ts`,

### DEFECT — the plugin cannot run potsherd when codex installs it

`plugins/codex/bin/potsherd` resolves through four steps. A marketplace install
satisfies **none of the first three**:

```
$ env PATH=/usr/bin:/bin sh $CODEX_HOME/plugins/cache/potsherd-local/potsherd/1.1.0/bin/potsherd --version
potsherd: this plugin has no potsherd to run, so nothing was done.

Looked in three places:
  1. …/potsherd/1.1.0/dist/potsherd.js                      (vendored in the plugin)
  2. …/potsherd/1.1.0/../../packages/cli/dist/potsherd.js   (the surrounding checkout)
  3. potsherd on PATH                                       (a global install)
… exit 127
```

`plugins/codex/` ships no `dist/` (the Claude plugin ships 2.4 MB of it), the
sibling `../claude-code/dist` is not copied by a marketplace install, and there
is no checkout above `$CODEX_HOME`. The **only** step that can succeed is
`potsherd` on PATH — and on the machine this was written on, PATH has
`/opt/homebrew/bin/potsherd`, so the same command prints `1.1.0` and looks fine:

```
$ sh $CODEX_HOME/plugins/cache/…/1.1.0/bin/potsherd --version   ;# full PATH
1.1.0
```

**That is the v1.1.0 regression class exactly: the environment that hides the
fault is the author's.** The plugin does the right thing about it (exit 127,
all three paths named, phase 0's "never silently do nothing" honoured), so this
is a packaging gap, not a code bug. It is also *disclosed* in `bin/potsherd`'s
own comments. But `08` should carry it: **the codex plugin is installable and
loadable and, installed from a marketplace today, does nothing.**

**RECOMMENDED:** either vendor `plugins/codex/dist/` the way `plugins/claude-code/`
is vendored — and then it **must** ship its own `package.json` with
`{"type":"module"}`, because `$CODEX_HOME` can be relocated under any project,
including a CommonJS one — or say in the README that the codex plugin requires a
built checkout beside it and is not marketplace-ready. `tests/plugin-install.test.ts`
now fails the moment a `dist/` appears without that decision being made.

### what could NOT be verified

**The MCP server was never registered.** With the plugin installed and enabled,
`codex doctor` reports `MCP servers 0` / `no MCP servers configured`. potsherd's
`.codex-plugin/plugin.json` declares no `mcpServers` key; OpenAI's own plugins
declare `"mcpServers": "./.mcp.json"` explicitly. The spec says the key
*supplements* default discovery rather than replacing it, so the default may
simply not cover `.mcp.json` at the root, or `codex doctor` may only count
config-declared servers. **Not resolved, and it needs a model call to settle
properly.** Cheap next step: add `"mcpServers": "./.mcp.json"` (and
`"hooks": "./hooks/hooks.json"`) to the manifest and re-run `codex doctor`.

**No model round trip.** `codex exec` reaches the API and gets
`401 Unauthorized: Missing bearer or basic authentication` — this machine has no
codex credentials that are ours to spend. `SessionEnd` therefore never fired,
so the indexing half of the plugin is still unexercised end to end.

$ potsherd show ses_fcf2 …
    1  24 aug 04:35  you

```

Neither `say hello` nor `Hello!` is anywhere in the index. The schema explains
it:

```
message(id, session_id, time_created, time_updated, data)          -- NO role, NO content
part   (id, message_id, session_id, time_created, time_updated, data)
```

The **role is inside the `data` JSON blob** and the **turn's text is not in
`message` at all** — it is in `part.data`, one row per content block. Column
discovery resolves `content → data` and dumps the metadata blob where the answer
should be. `03 §10`'s rule (discover, never hard-code) worked as designed; the
candidate lists just do not describe a store that keeps its payload in JSON and
its text in a child table.

Pinned in `tests/adapters/opencode.test.ts` (describe *"a real opencode-ai
1.18.21 store (T10.12)"*) against a builder added to
`tests/fixtures/opencode/make-opencode-db.mjs` (`buildOpencodeReal`).

**RECOMMENDED EDIT — `packages/core/src/adapters/opencode.ts`.** Two additive
steps, in this order:

1. when the resolved `role` column is absent but the resolved content column
   holds parseable JSON with a `role` string, take the role from inside it;
2. when the store also has a `part`-shaped table (a child with `message_id` and
   a `data` column), read the turn text from its rows in `id` order, taking
   `data.text` where `data.type === 'text'`, and fall back to today's behaviour
   when it is missing.

Both are the same widening argument the header already makes: *"Adding a
candidate name to those lists can only make a store that was unreadable
readable."* Neither changes what `snake.db` or `camel.db` parse to.

**NOT APPLIED HERE** — a `part` join is a new read path, not a correction, and
this is one store from one version.
