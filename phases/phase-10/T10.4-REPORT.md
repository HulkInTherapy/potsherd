Well inside §A2's "~2 s". Nothing about acquisition is imported until `initEmbeddings()` is called,

### wasm vs native embedding throughput
Same 60-exchange corpus (mean 1,404 chars), same weights, same pooling, one exchange per forward
pass, four threads, through the shipped `generateEmbedding`:

| measurement | wasm (onnxruntime-web 1.27.0) | native (onnxruntime-node 1.24.3) | ratio |
|---|---:|---:|---:|
| early run, light machine load | **233.9 ms** / exchange | **35.8 ms** / exchange | **6.5×** |
| later run, load average 11.6 (other workers on this box) | 324.9 ms | 85.9 ms | 3.8× |
| repeat of the same | 353.0 ms | 91.2 ms | 3.9× |

So **4–7× slower**, and the clean-machine figure is 6.5×. That is above §A2's 5× threshold, so
**newest-first shipped** (`ORDER BY ts IS NULL, ts DESC` in `embedPending`), and it costs nothing on
the runs where the ratio is lower.

Thread sweep on wasm, per exchange: 1 → 536 ms, 2 → 270 ms, 3 → 278 ms, **4 → 269 ms**, 6 → 330 ms,
8 → 554 ms. The same shape the native runtime showed, so the existing `embedThreads()` heuristic
(half the logical cores, capped at four) serves both unchanged.

**Vector agreement, wasm vs native, same input:** cosine **0.9983 mean, 0.9950 worst** over the 60
exchanges. Isolated to the runtime: the two tokenizers produce byte-identical token ids on every
input tested, float64 pooling accumulation changes nothing (cosine 1.000000 against float32), and
`graphOptimizationLevel` disabled/basic/extended/all all land at 0.9981–0.9983. It is
onnxruntime-web's int8 kernels choosing q8 activation scales differently, and there is nothing above
them to fix. `EMBEDDING_VERSION` was therefore **not** bumped: 5e-3 of cosine is the same order as
the batch-vs-single difference upstream already tolerates, and bumping would force every existing
user to re-embed their whole archive.

I did **not** touch the gate, the RRF weights, the model or the dtype to recover it. What I ruled
out and why:

- **fp32 weights** (`onnx/model.onnx`, 133 MB) would remove the quantization disagreement entirely,
  but it triples acquisition to 147 MB — against §A2's "~34 MB order-of-magnitude" — and overrides a
  dtype the header comment records as upstream's measured choice.
- **onnxruntime-web 1.24.3**, version-matched to the native build, was fetched and measured: cosine
  0.998782 (vs 1.27.0's 0.998263) at 401 ms/exchange (vs 234). A 71 % throughput cost for 5e-4 of
  cosine, and nowhere near enough to move a rank.
- **Using native when it happens to be installed** would make CI green and ship the untested path.

This is a decision for the orchestrator, and there are only two honest shapes: re-base the phase-3
gate on the runtime that actually ships (re-derive its thresholds from a wasm run), or widen the
eval set — 25 queries gives σ ≈ 2.2 queries, so a gate with a margin of one has no margin at all.

### sqlite-vec vs brute-force cosine — the measurement that decided it

Median of twelve top-25 searches, identical data, identical results, on the reference machine:

| n vectors | brute-force scan (JS, via the `match()`/`potsherd_vec_distance()` UDFs) | sqlite-vec (native vec0) |
|---:|---:|---:|
| **1,678** (the real archive) | **4.7 ms** | 0.9 ms |
| 10,000 | 32.0 ms | 4.2 ms |
| 50,000 | 190.4 ms | 20.8 ms |
| 200,000 | 2,330.8 ms | 82.1 ms |

At the size potsherd actually indexes the entire native dependency buys **3.8 ms** on a `find` the
audit measured at 23–270 ms. That is a rounding error paid for with a whole class of install failure
(unsupported platform, stripped `node_modules`, `enable_load_extension` off, hardened-runtime
signature check, and — the common case — simply not installed).

**Decision: the scan is the storage and the search, on every machine. `sqlite-vec` is no longer used
to answer a query at all.** It is still loaded once, for one job: reading vec0 rows out of a database
built before this, during migration 10, so nobody loses embeddings they already paid for.

I did *not* keep it as an optional fast path. Dual storage means two write paths, two schema
branches and two sets of failure modes for 3.8 ms; a single path that works everywhere is the
lighter way the product law asks for. The crossover is documented in `vec.ts`: past ~50,000
exchanges — thirty times the reference archive — an index starts to earn its keep, and that number
is the thing to re-measure against, not a hunch.

The compatibility trick, because it is the load-bearing part: `vec_exchanges`, `vec_cards` and
`vec_ghost_prompts` are **views** over blob tables with `INSTEAD OF` triggers, so `INSERT`, `DELETE`,
`COUNT(*)` and `SELECT id, embedding` all work verbatim. For the KNN query, SQLite compiles
`embedding MATCH ?` to the application-defined function `match(?, embedding)` — potsherd defines it;
it records the query vector for the statement and admits every row — and the view's `distance`
column is `potsherd_vec_distance(embedding)`, which scores against that recorded vector. WHERE is
evaluated before the output columns of the first row, so the vector is always present, and when it
is not the distance is `MAX_VALUE` rather than a wrong number. Verified on **both** drivers against
a JavaScript ground truth: identical ids, identical distances, zero error. `recall.ts` was not
touched.

5. **The real network fetch WAS exercised**, four times, against `cdn.jsdelivr.net` and

## 6. new environment variables (all optional, none required for anything to work)

| var | effect |
|---|---|
| `POTSHERD_EMBED_BACKEND` | `native` forces `@huggingface/transformers` when it is installed. Default is wasm. Used for the benchmark above. |
| `POTSHERD_RUNTIME_BASE`, `POTSHERD_MODEL_BASE` | Redirect acquisition at a mirror, or at a local server. The tests use them. |
| `POTSHERD_OFFLINE` | Never reach the network. `HF_HUB_OFFLINE` / `TRANSFORMERS_OFFLINE` are honoured too. |
| `POTSHERD_EMBED_WORKER` | Internal: turns `index` into the background embedder. Not a flag, not documented to users. |

`POTSHERD_NO_VEC` still exists and now only disables the (unused) legacy extension load.
