## c. How the full query still contributes

Four ways, none of them decorative.

1. **The exact pass runs first and is untouched.** Rung one is `AND` over every token. Where
   the words as typed work, they still win and the keyphrase never runs.
2. **The any-word pass runs last and is untouched.** When the keyphrase finds nothing, every
   token the user typed is tried again, prefix-matched, exactly as before. Rung two can only
   ever *replace a relaxation*, never a match. Pinned by
   `tests/recall.test.ts › falls all the way back when the distinctive words find nothing`.
3. **The word that gets dropped is always a common one.** The keyphrase is selected *by*
   rarity, so every term it drops has a document frequency ≥ every term it keeps. A rare word
   that only appears in the long phrasing is by construction the first thing kept, not the
   first thing thrown away. Pinned by
   `tests/recall.test.ts › a rare word is never the word that gets dropped`, which asserts
   `max(df of kept) ≤ min(df of dropped)` over two long queries.
4. **`coverage` still counts every content word.** The keyphrase decides which rows become
   candidates; the denominator of the confidence score is unchanged. That is why the correct
   session in §b is `#3` and still `none` — the fusion promoted it and the calibration
   refused to overstate it. `tests/recall.test.ts › the full query is still what the answer is
   judged on` asserts `coverage == 1/5` on the audit's query.

There is also one place a word *is* genuinely set aside: a term at df 0. `selectTerms` drops it
from the keyphrase because a word in no document cannot find anything — conjoined it returns
nothing, disjoined it contributes nothing. It stays in the any-word fallback. This is T10.1
§d1's IDF objection answered directly rather than dodged: T10.1 measured `kept`, `even` and
`fine` at df 0 and observed that `log(N/df)` hands exactly those words the highest weight.
That measurement is correct, and it is a measurement about *scoring*. Extraction asks a
different question — not *how surprising is this word* but *which of these words will find the
conversation* — and under that question a df-0 term is the least useful word in the query, not
the most. `tests/keyphrase.test.ts › drops df-0 terms rather than ranking them first` pins it,
and `has no opinion at all when every word of the query is absent` pins the safety valve.

## d. Proof a short query is unchanged

The guarantee is **structural, not empirical**. `recall()` builds the keyphrase rung only when
the keyphrase is a *strict* subset of the tokens the any-word pass would use. `find "pgbouncer"`
has one content word, its keyphrase is that same word, the subset is not strict, and the
expression is never built — so the ladder is the v1.1.0 ladder, unchanged, for every query
that was already distinctive.


Same session, same rank, same `strong`, same fused score to four decimals.

## e. The vector-hit control gap — diagnosis, and what I did

### The brief's premise is wrong, and that matters

> *"…and **only when vectors are on** — with `--no-embed` it correctly says `no match`. So a
> semantically-plausible vector hit is reaching `weak` on a query whose distinctive term is
> absent."*

It is not a vector artefact. Measured three ways on `793c369`:

| how | result |
|---|---|
| `find "bluetooth on the checkout page"` (vectors on) | 2 rows `weak` |
| `find "bluetooth on the checkout page" --no-vec` | **2 rows `weak`** |
| `pnpm evals` on an index built with no embedding model at all | **`FAIL zero rows / 2 rows weak`** |

And `evals/run.ts:180` runs its controls at `vectors: false` — so the failure the eval set
reports was *never* being produced with vectors on. Whoever wrote the brief's paragraph
inferred the vector story from the fact that a semantic hit was plausible. It is worth saying
because the inferred cause would have sent the fix into `vec.ts` or the cosine path, and there
is nothing wrong there.

### What it actually is

`coveredTerms` is a **uniform partition over the query's content words**. For
`bluetooth on the checkout page` the quotable terms are `bluetooth · checkout · page`, and a
checkout session shows two of them:

```
coverage            2 / 3                       = 0.667
× (0.6 + 0.25×1 + 0.15×0)                       = 0.567   ≥ WEAK_FLOOR (0.5)
```

Missing `bluetooth` costs exactly what missing `page` would. `WEAK_FLOOR`'s own docstring says
the constant means *"a row must show a clear majority of the **distinctive** words that were
typed"* — and 2 of 3 is a clear majority of *the words*. The constant was keeping a promise
about a quantity nothing was measuring. A two-topic question can therefore be answered at
`weak` by a row that has one topic and not the other, and the half it is missing is the half
that named the subject. `a86656f1`'s title is *"Flaky end-to-end test on the checkout page"* —
two of the three terms, verbatim, in six words.

`evals/QUERY-SET.md` §7(b) had already reached the same place from the other side ("one half of
the query matches one session's title almost verbatim") and correctly left it red.

### What I did

`KEY_TERMS_REQUIRED = 1` in `calibration.ts`: **a row that cannot show the single most
selective term of the question is capped at `none`, whatever it scores.**

It is a *necessary condition*, not a weight — which is the whole difference between it and the
IDF-weighted coverage T10.1 rejected. Nothing multiplies a score by a rarity. A term's rarity
decides only whether it is at the head of `keyphrase.terms`, and that head is chosen by
relative rank on this index, never by a magnitude. It is applied as a **ceiling**, so
`score` keeps reproducing `coverage × (base + …)` from the numbers printed beside it and
`--explain` stays debuggable; the label is what is refused, not the arithmetic. It composes as
a `min` with F6's `ROUTING_CEILING`, so a card still cannot claim `strong`.

Result: **all six confidence controls pass**, including the red one, and the three that were
already passing withhold *fewer* rows than before (they were withholding correct rows too).

### What it costs, measured, because it is not free

At the floor `find` actually runs at (`minConfidence: 'weak'`), over the 60 recall queries,
bm25-only:

| | before | after |
|---|---|---|
| gold session visible at all | 10/60 | **8/60** |
| total rows shown | 12 | 9 |
| precision of what is shown | 83% | **89%** |

and with vectors on: gold visible 13/60 → 10/60, rows 18 → 12, precision 72% → 83%.

Three queries lost their answer at the floor and one gained it. The three losses, and they are
the honest finding of this section:

```
eu region reporting a day late                            required term "reporting"
changes the user had already undone came back             required term "came"
the button that looked broken while a lookup was running  required term "looked"
```

`came` and `looked` are ordinary English verbs. They are at **df 2** here because the fixture
is 120 exchanges — a corpus that small has no separation between common English and a
technical term, so the "most selective word" is sometimes a verb rather than the subject. On a
433 MB archive `looked` and `came` have df in the hundreds and the rarest term is reliably the
topical one. **This is the one rule in the task whose discrimination is a function of corpus
size, and it degrades in the direction of the small corpus, not the large one.** I would expect
it to be strictly better on the reference archive and I cannot prove that from here — please
re-measure. The lever if it is wrong: `KEY_TERMS_REQUIRED = 0` switches the condition off
entirely, one character, and the bluetooth control goes back to red.

### The choice I made after measuring, disclosed

`KEYPHRASE_RULE.keepRatio` is a half; the **rounding** was a real fork and I measured both
before choosing.

| variant | bm25@5 | bm25@1 | hybrid@5 | hybrid@1 | wide half | tight half | answer's rank in §b |
|---|---|---|---|---|---|---|---|
| baseline | 32 | 24 | 52 | 27 | ✓✓ | ✓✓ | absent from top 5 |
| half rounded **down** | 42 | 27 | 48 | 29 | ✗ `≥ vectors` | ✓✓ | **#1** |
| half rounded **up** (shipped) | 40 | 26 | 51 | 27 | ✓✓ | ✓✓ | #3 |

Rounding down extracts harder: bigger bm25 win, the answer at #1, and a −4 on hybrid@5 that
breaks the `hybrid ≥ vectors` half of the gate. Rounding up is the version I shipped, and the
reason I give is the one in ACCEPT item 3 — **discarding a word the user typed is the
destructive operation, so the rounding should be the conservative one** — not the fact that it
keeps a gate clause green. I am flagging it anyway, per the brief's instruction, because I
would rather you weigh the two tables yourself than take my word for which principle came
first. Both are one character apart in `keyphrase.ts:selectTerms`.

Two other variants were measured and rejected on their numbers, and they are listed because a
rejected variant is evidence:

- **Union instead of replacement** (keyphrase rows prepended to the any-word rows, nothing
  removed). bm25@5 **31**, hybrid@5 51 — i.e. it erases the fix. The bm25 win comes precisely
  from the noise rows *ceasing to be candidates*; keeping them at ranks 3, 4, 5 keeps their
  RRF contribution and the audit's ghost stays at #1. A genuinely appealing design that does
  not work, and the reason rung two replaces rather than appends.
- **Compounding the relaxation penalty** (`RELAXED_PENALTY^rung`, so the any-word pass is worth
  0.36 when a keyphrase pass existed). bm25@5 43, hybrid@5 50, hybrid@1 **27 = bm25 27**,
  which breaks the `> bm25` half. Discarded; the penalty is flat, exactly as it was.

## g. What I could not do, and why

1. **The floor still hides the answer to a long natural-language query.** §b's after-view is
   `no match, 14 withheld`. The ranking is fixed and the calibration is not, because
   `coverage` for a correct session on a five-content-word question is 1/5 and `WEAK_FLOOR` is
   a pinned stopping rule (`plans/08` rule 3, T10.1 §d1). Three coverage variants that would
   lift it were considered and all three fail something that matters more:
   - *coverage over the keyphrase instead of all content words* — measured: it makes the
     bluetooth ghost `strong` for `bluetooth on the checkout page` (1 of 1 key terms covered),
     which turns a zero-row control into a one-row one. Rejected on the control.
   - *lowering `WEAK_FLOOR`* — re-litigating a constant I was told not to, and it re-admits
     everything T10.1 measured out.
   - *IDF-weighting coverage* — T10.1 measured and rejected it; §c says why the extraction
     rule is not the same thing and why the rejection still stands for scoring.

   My honest read: F8-the-ranking-finding is fixed and F8-the-experience is half fixed. The
   other half is `WEAK_FLOOR` on long queries, it is the gate's owner's decision, and the
   evidence for it is T10.1 §d1 plus the table in §e.
2. **`--explain` does not print the keyphrase.** `packages/core/src/render/find.ts` and
   `packages/cli/**` are outside the DELIVER list. `recall()` returns `keyphrase` and
   `keyphraseLists` and the data is there the moment somebody renders it; the human view
   currently says `relaxed to any-word matching` for a keyphrase pass, which is true (it *is*
   any-word over the distinctive words) but less informative than it could be. §i has the
   lines.
3. **`--json` does not carry it either** — same reason, `packages/cli/src/commands/find.ts` is
   reserved. §i.
4. **I could not measure on the 433 MB archive.** Everything here is the 0.5 MB fixture. §e
   names the one rule I expect to behave *better* there and cannot demonstrate.
5. **`packages/core/src/index.ts` is reserved**, so neither new module is exported from the
   barrel. Tests import from source, the way `tests/calibration.test.ts` and
   `tests/cards-lane.test.ts` already do. §i.

### One defect found outside scope, reported not fixed

`evals/run.ts:180` runs the confidence controls at `vectors: false` while the recall queries
run at each mode's own setting. That is defensible — the controls are about the floor, not the
fusion — but it means **no control in the set has ever exercised the floor with vectors on**,
and the brief for this task inferred a vector cause for a failure that could not have come from
there. A `no-match` control that passes on bm25 and fails on hybrid would be invisible today.
`evals/**` is reserved; I did not touch it.
