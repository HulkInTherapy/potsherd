# T10.13 — open-thread precision at n ≥ 30, and `link --suggest` re-measured

**status:** in progress. This section — the judging rule — was written and committed
**before the first candidate existed**, so that a reader can tell method from taste.

---

## 0. the judging rule, pre-registered

The judge is **me, the host agent** (Claude Code, Opus). There was no other model available on
this machine: the resolution ladder's rung 2 (`claude --print`) answers *"Not logged in"* here and
rung 3 (an API key) is absent, so every model-shaped step in this measurement was done by the agent
through a hand-built version of the phase's own `--readers-out`/`--filter-in` seam. That is rung 1,
and it is the rung the phase says is the primary one; it is also the reason a reader should treat
the *usefulness* half of this measurement as one competent reader's judgement rather than a
consensus.

A candidate is one raised row of the rule pass: **"decided in A, never seen in B"**. Each is judged
on two independent axes, and the two are never collapsed into one number.

### axis 1 — ABSENCE (the half the tool asserts as fact)

| verdict | means |
|---|---|
| `absent` | no card in project B, and no exchange of any project-B session, states this decision, restates it, or acts on it |
| `present` | some project-B session does state or act on it — the tool's factual claim is **wrong** |
| `undecided` | the evidence does not settle it |

Method for `absent`: read every project-B card's `decisions`, `open_threads`, `topics` and `files`,
then run a content-token search over project B's raw `exchanges` for the decision's distinctive
tokens. Absence is only asserted after the raw-exchange search comes back empty — B's cards alone
are not enough, because a card is a summary and can omit what the session did.

### axis 2 — WORTH RAISING (the half that decides whether the feature earns its screen)

`worth` requires **all four**:

- **(a) real relation.** A and B are the same kind of work, or share a real artifact — a file, a
  schema, a tool, a format. Shared *process vocabulary* ("audit", "plan", "phase", "review") is not
  a relation.
- **(b) portable.** The decision is a rule, convention, threshold, or technique that would apply
  again in B. A fix local to A's own code, a rename, a one-off, or a decision *about A itself* is
  not portable.
- **(c) actionable.** Specific enough to act on without re-opening the session.
- **(d) live.** B is work a reminder could still land on, not a project that ended before A's
  decision was made.

Failing any one of (a)–(d) is `not-worth`. Anything I genuinely cannot settle is `undecided`, with
the reason recorded, and **undecided rows are counted on their own and folded into neither side**.

### axis 3 — the cosine's positive side, which has never had one

The old claim's worst line is *"the cosine's positive side is n = 0"*: nobody has ever seen a case
where project B genuinely restated A's decision, so nobody has ever seen `MENTION_COSINE` do the job
it exists for. This measurement goes after that directly, by also collecting the pairs the bar
**suppressed** — decision-in-A/project-B pairs that passed rules 1–5 and were rejected only by rule
6 (mention cosine ≥ 0.35) — and judging each:

- `true positive` — B really did say this; the bar was right to withdraw the candidate.
- `false positive` — B did not say it; the bar cost a real catch.

and, symmetrically, every axis-1 `present` verdict is a **miss** of the bar: B did say it, the
cosine scored below 0.35, and the candidate was raised anyway.

### what is *not* being tuned

No threshold moves as a result of this measurement. If the data argues a constant is wrong, the
argument and the data are reported and the constant stays where it is (ruling, T10.13 brief).

### how the corpus was built, and the bias that follows

The archive on this machine holds 345 indexed sessions; `cards/plan.ts`'s `MIN_EXCHANGES = 3` makes
**46** of them cardable and the other 299 too short. 46 is therefore the hard ceiling on cards, and
every candidate below comes from those 46 across 12 distinct projects. The cards were written by the
host agent through the seam rather than by `haiku` through rung 2, because rung 2 is not reachable
on this machine. Two consequences, both stated rather than hidden:

- the cards are **better** than a `haiku` card run would produce, which if anything makes the rule
  pass look *better* than it would on a bare-CLI machine;
- the extract step ran **whole-session rather than chunked**, because the seam hands the agent the
  whole transcript; the shipped path map-reduces long sessions over 60 kB chunks.

Everything downstream of extraction is the shipped code, unmodified: `validateCard`,
`normaliseCard`, `verifyCard` (with the real cached bge-small embedder, so the evidence cosine is
real), `dedupeCard`, `writeCard`, then `openThreadCandidates` and `suggestLinks` as they ship.

## 1. the corpus, and the true ceiling

The index was built into a kept evidence directory with `HOME` relocated, so nothing was written
into any of the seven harness trees:

```
env -u CLAUDE_CONFIG_DIR -u POTSHERD_DIR -u XDG_CONFIG_HOME -u NODE_PATH HOME="$EV/home" \
  node packages/cli/bin/potsherd.js index --full --no-embed \
    --claude-dir "$REAL_HOME/.claude" --potsherd-dir "$EV/home/ps"
```

`--claude-dir` points at the live Claude Code tree (a read); the other six harnesses resolve under
the relocated `HOME`, and the three that exist on this machine were **copied** into it first, so
even a hypothetical write could not reach the originals.

| | |
|---|---|
| sessions indexed | **345** — claude 336 (48 top-level, 288 sidechains), cursor 4, pi 4, codex 1 |
| exchanges | 1,714 · 23,778 tool calls · 223 redacted |
| distinct projects | 18 |
| full index | 24.0 s, 451 MB read |
| **sessions `card` will card** | **46** — the other 299 are below `MIN_EXCHANGES = 3` |
| projects holding a cardable session | **12** |
| ghosts | 0 (`rescue` was not run; there are none recovered on this machine) |

**46 is the true ceiling on cards, and it is a property of the archive, not of the effort spent.**
The task asks for open-thread precision at n ≥ 30, where n counts *candidates*, not cards: one card
can raise several. Whether 46 cards over 12 projects clears 30 candidates is answered in §2, and if
it does not, 46 is the number that explains why.

## 2. open-thread precision at n = 109

The rule pass was run over the 46 cards with the limit raised so that nothing was truncated:
`openThreadCandidates(db, everyCardedSession, { limit: 500 })`. It raised **109 candidates** — after
the module's own collapse of one line per decision — from **192** (decision, project B) pairs that
reached rule 6, across **35 ordered project pairs**. n ≥ 30 is met with room to spare; the ceiling
that mattered was cards, not candidates, and 46 cards were enough.

| | phase 4 (the claim being replaced) | **T10.13** |
|---|---|---|
| cards | 45 (20 session + 25 ghost) | **46 session cards, 0 ghosts** |
| projects with a card | 18 | **15** |
| pairs reaching the mention check | 194 | **192** |
| candidates raised | 26 collapsed, 8 read | **109 raised, 109 read** |
| **judged absent from B** | 8 / 8 | **99 / 108 = 91.7%** |
| **judged worth raising** | 1–2 / 8 | **18 / 100 = 18.0%** |
| undecided | 0 | **1** (absence), 0 (usefulness) |

### the two numbers, said plainly

- **The absence claim is right about nine times in ten, not ten times in ten.** Phase 4's 8/8 was
  not wrong; it was eight. At 108 decided cases the rule pass makes a false factual claim in **9**
  of them: project B does state, restate, or act on the decision the tool says it never saw. Those
  nine are listed with their cosines in `T10.13-MEASUREMENT.md`.
- **The usefulness claim survives almost exactly.** Phase 4 read 1–2 of 8 as worth raising; over
  109 the figure is 18%, and over the top 8 by score — the screen `ask` actually prints — it is
  **1 of 8**. A ten-fold larger sample did not move it. This is the number that decides whether the
  feature keeps its place, and it is not flattering.

### why the 82 are not worth raising, by kind

Two failure kinds account for 71 of the 82, and both were named by phase 4 on eight cases:

| kind | n | what it looks like |
|---|---|---|
| **vocabulary** (R2) | 38 | two projects that share only generic, tool or process words — a research tool both use, a filename that exists everywhere, the words "phase", "plan", "audit", "post" |
| **local to A** (R1) | 33 | a decision about A's own folder, its own file layout, or how that one session was run. Genuinely absent from B, and meaningless there |
| **wrong way** (R3) | 9 | one programme recorded under two directories, where B is the *upstream research* the decision already consumed. The reminder has nowhere to land |
| **directory artefact** (R5) | 2 | A and B are the same body of work under two working directories, so the "other project" is not another project |

R3 and R5 are new names for something phase 4 could not see at n = 8: **`project` is a working
directory, not a subject.** Eleven of the 109 candidates pair two directories that hold one piece of
work, and `sameProject()`'s path-containment test cannot catch them because the directories are
siblings, not parent and child.

### what was missed

The measurement can report *false* positives and cannot report false negatives in general — a
decision that should have been raised and was not leaves no trace to count. One class is
measurable, though, and it is a defect:

> **The rule pass compares a decision only against project B's `decisions` and `open_threads`.** A
> card's `topics`, `title` and `summary` are never consulted. Three of the nine false positives
> (C008, C023, C093) are cases where **B's own card carries the decision as a topic** — the index
> already held the answer and the comparison could not see it. This is in `loadCards`, where
> `mentions` is built from `decisions` and `open_threads` alone.

Reported, not fixed: widening `mentions` changes what the verb raises, and this task was told to
measure, not to tune. It is the highest-value single change available to this feature and it costs
nothing at query time.

## 3. the cosine's positive side is no longer n = 0

This is the part of the old claim that was not a small sample but an absent one.

**Nine true positives were found, and `MENTION_COSINE` caught none of them.**

| | |
|---|---|
| pairs reaching the mention check | 192 |
| pairs the bar **suppressed** (cosine ≥ 0.35) | **0** |
| genuine restatements found among the raised candidates | **9** |
| of those, cosine ≥ 0.35 | **0** |
| their cosines | min 0.0910 · median 0.1217 · **max 0.2309** |

The negative distribution re-measured almost exactly as phase 4 measured it (median 0.101 vs 0.089,
p99 0.2774 vs 0.298, max 0.3145 vs 0.3223 — see `T10.13-MEASUREMENT.md`). Laying the positives over
it gives the result the feature has been waiting for since phase 4:

> **The largest true positive scores below the 99th percentile of the non-matches.** A cut that
> admits it would withdraw more than 1% of the non-matches; a cut low enough to catch the *median*
> true positive would suppress most of the corpus. The two distributions do not merely overlap —
> the positives sit inside the bulk of the negatives.

Phase 4 inferred this from synthetic paraphrase pairs and said so honestly. It is now measured.

**Nothing was changed.** `MENTION_COSINE` stays at 0.35 and `MEASURED_NONMATCH_MAX` stays at 0.3223,
because the finding is not "the number is wrong" — it is "no number is right", and choosing a
different one would only trade nine missed catches for a hundred wrong suppressions. The honest
consequences are two, and both are for somebody else's task:

1. the module's own comment already says the mention check is not what makes the feature safe. That
   is now the measured position rather than the inferred one, and the comment is updated to say so.
2. if this is ever to work, it needs a **different statistic** — the embedding cosine the module's
   comment already nominates, which needs the pinned synchronous signature to change — or the far
   cheaper fix in §2: compare against B's topics as well as B's decisions.

## 4. did threads change any verdict? No, and the reason is worth recording

`deriveThreads` found **2 multi-session threads** in this archive (4 sessions in total), and
`threadOf` was evaluated for every one of the 109 candidates against every project-B session named
in it.

**`sameThreadWithB` is false for all 109.** Not one candidate pairs two sessions that are really one
fork/resume chain.

The reason is structural rather than lucky: both derived threads have all their sessions inside one
project *or* inside a directory and its own subdirectory, and `sameProject()` already excludes both
of those by path containment. So on this archive the thread check is subsumed by the check that was
already there. The hypothesis in the brief — that an "open thread" could be the same thread under
two ids — is **sound but does not fire here**; it would fire on an archive where a resumed session
changed to a *sibling* directory, and that is exactly the R5 shape (2 cases) that
`sameProject()` misses today for a non-thread reason.

Worth recording for whoever picks this up: **the cheap version of the thread check is already
possible and would not have changed one row**, so it should not be added to `open-threads.ts` on the
strength of this corpus.

## 5. `link --suggest`, re-measured

Replacing *"5 raised of 20 over 45 cards, 2 worth accepting"*.

| | phase 6 (the claim being replaced) | **T10.13** |
|---|---|---|
| cards | 45 | **46** |
| at the shipped default (`DEFAULT_LIMIT = 5`) | 5 raised of 20 considered | **5 raised of 20 considered** |
| worth accepting, of those 5 | 2 | **5** |
| raised at limit 200 | — | **18 of 40 considered** (40 is the internal cap) |
| worth accepting, of 18 | — | **12 (67%)** |
| already-linked pairs dropped | — | 0 |

The verb looks far better than open threads, and the reason is that it asks a much weaker question:
*are these two sessions worth connecting?*, not *is this decision absent from that project?*. A link
survives a bad decision text as long as the pair is right.

**The 5-of-5 needs its caveat printed with it.** All five rows on the default screen are one
relationship — a design project and the build project it fed, in both directions, plus one of its
subdirectories — because `suggestLinks` de-duplicates on the **session** pair, not the **project**
pair. Across the full 18, the 12 accepted rows cover only **6 distinct project relationships**.
A user who accepts the screen gets five links into one relationship and none into the other five.

That is a real defect and it is reported, not fixed: a project-pair cap in `suggestLinks` would
change what the verb returns, which is a behaviour change this task was not asked to make.

## 8. what could not be done, and why

1. **No model was reachable, so the model pass was not re-measured.** Rung 2 (`claude --print`)
   answers *"Not logged in"* on this machine even with `HOME` and `CLAUDE_CONFIG_DIR` left alone,
   and there is no API key. `confirmOpenThreads` — the pass that drops unconfirmed candidates before
   `ask` prints them — was therefore **not** exercised against these 109. Phase 4's figure for it
   (1 of 8 confirmed, agreeing with 6 of 8 hand labels) stands unreplaced. Everything measured here
   is the **rule pass**, which is what both `ask`'s candidate set and all of `link --suggest` rest on.
2. **The cards were written by the host agent, not by `haiku`.** That is rung 1 of the phase's own
   ladder and the only rung available, but it is a bias in the optimistic direction: better cards
   mean better topics and files, which means a *more* related-looking overlap than a bare-CLI user
   would get. The extraction was also whole-session rather than chunked.
3. **Ghosts were not measured.** `rescue` recovers none on this machine, so the asymmetry the module
   turns on — weak evidence may withdraw a candidate, never raise one — has no case here.
4. **False negatives cannot be counted in general.** A decision that should have been raised and was
   not leaves no artefact. The one measurable class is in §2 and it is a defect.
5. **The ceiling that bound this measurement was cards, not candidates.** 46 of 345 sessions are
   above `MIN_EXCHANGES = 3`. Had 30 candidates been unreachable, 46 would have been the number to
   report; it was reachable, and comfortably.
6. **Ids are not printed as their first eight characters**, against the brief. The reason is the
   privacy guard, and it is set out at the top of `T10.13-MEASUREMENT.md`.

## 10. defects found outside scope — reported, not fixed

1. **`loadCards` cannot see what the index already holds.** `mentions` is built from project B's
   `decisions` and `open_threads` only; `topics`, `title` and `summary` are never compared. Three of
   the nine false positives are decisions B carries as a *topic*. `packages/core/src/open-threads.ts`,
   in scope for this task but a **behaviour** change, which the brief forbids. It is the cheapest
   improvement available to this feature.
2. **`suggestLinks` de-duplicates on the session pair, not the project pair**, so one strong
   relationship fills the default screen — measured: 5 of 5 rows, and 6 of 12 accepted rows overall.
   `packages/core/src/link-suggest.ts`, same reason.
3. **Three files still cite the superseded 1–2-of-8 figure**, all outside this task's deliverable
   list and all reserved:
   - `packages/core/src/render/ask.ts:310` — a comment justifying a rendering choice by the old rate.
   - `packages/cli/src/commands/link.ts:45` — the same, justifying the disclosure branch.
   - `docs/09-RUNNING-WORKERS.md:471` — the figure quoted in prose.

   None of the three is *wrong* about the open-thread rule pass's usefulness — 18% is the same story
   as 1–2 in 8 — but all three say `8` where the evidence is now 109, and the `link.ts` one now
   disagrees with the constant it is describing.
4. **`sameProject()` is path containment only**, so two sibling directories holding one body of work
   are treated as two projects. Two candidates (R5) and nine more (R3) are this shape. Threads do not
   catch it either: see §4.

be"* **fails on this branch**, and it is not a defect in the change:


**`plugins/**` is reserved to this task, so it was not re-vendored.** The integrator must run:
