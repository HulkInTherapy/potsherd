## D. what stops a note being cited as transcript evidence

Split honestly into what is code and what is not.

**Code, and structural — the `ask` pipeline.** `ask.ts`'s `filterAnswer` resolves every proposed
quote to a `(sessionId, seq)` pair inside `EvidenceSource.units`, and those units are built from
`exchanges` rows and nothing else. A quote whose `seq` is not in that map is dropped as
`unresolved-seq`; a quote whose text is not a literal substring of the stored exchange is dropped
as `not-a-quote`. **A note has no `seq` and its text is in no exchange**, so both gates refuse it
before a user sees it. This is exactly the stop that makes a *card* uncitable, and `ask.ts` says
so in its own words: *"it has no `seq`, so a quote taken from it resolves to no unit in
`filterAnswer` and is dropped with the sentence that leaned on it."* I did not touch `ask.ts`,
which is the strongest form of the guarantee: notes are not in the citable set because no code
puts them there.

**Code, and structural — the store.** Notes live in `notes` / `notes_fts` and in no other table.
A test asserts the boundary at the level where it would actually break: after
`addNote(… 'quenepa …')`, `SELECT count(*) FROM exchanges_fts WHERE exchanges_fts MATCH
'"quenepa"'` is **0** and `notes_fts` is **1**, and the `exchanges` row count is unchanged.

**Convention, and I am saying so plainly.** Three gaps:

1. **Labelling is labelling.** `kind: "note"`, `citable: false` and the human line
   *"assertions by their authors, not transcript"* stop a *reader* confusing the two. They do
   not stop a *program*. Nothing rejects a caller that reads `decided` out of `--json` and
   pastes it under `SOURCES`.
2. **`verifySources` checks the id, not the provenance of the text.** `packages/mcp/src/tools/
   sources.ts` refuses a `SOURCES` field that is not an id8 or that resolves to nothing — that is
   F3's fix, and it is real. But a note's `sessionId` *does* resolve, so a `SOURCES` line naming
   that session passes. It was never built to check where a quote came from; `filterAnswer` is
   the layer that does, and it only runs on the `ask` path.
3. **Nothing prevents a future contributor from adding notes to `EvidenceSource.units`.** There
   is no guard test for it. **Recommended, and out of my scope** (`ask.ts` is T10.5's): a test
   asserting that `packages/core/src/ask.ts` contains no reference to `notes` or `notes_fts` —
   the same shape as `tests/llm.test.ts`'s "no offline verb reaches `@potsherd/bridges`". Until
   that lands, item 4 is *"code stops it on the one path that matters, and convention holds the
   rest"*, not *"code stops it"*.

## E. what a second write does, and why

**It appends. A second note is a second row; nothing is rewritten, superseded or refused.**

Measured: `note 2` in §B reports `1 earlier note on this thread is still there`, and reading the
lane back prints both. `tests/notes.test.ts` asserts the older row afterwards with
`expect(all[1]).toEqual(one.note)` — field for field, not "still present".

Why, against the two alternatives:

- **Supersede** would mean writing to a row that had already been written, which is the one
  property this table exists to not have. It also destroys the most interesting thing in the
  lane: an agent that noted a decision at 10:00 and changed its mind at 16:00 has recorded *that
  it changed its mind*, and both halves are worth more than either.
- **Refuse** would fail at precisely the moment the agent has something new to say, and would
  teach agents that `note` is a thing you get one shot at — which makes them not use it.

There is deliberately **no `superseded_by` column**. "Which note is current" is derived at read
time (`MAX(id)`; `threadNotes` returns newest first) rather than stored, so it cannot go stale
and cannot be left wrong by a write that stopped halfway. Ordering is by `id` and not by
`written_at`, because `written_at` is a value the caller may supply and `id` is the order the
store actually accepted rows in — the only ordering it can vouch for.

Over-length input **refuses** rather than truncating (`MAX_NOTE_FIELD = 2000`, error names the
fix: *"shorten it, or leave two notes — the lane is append-only, so both are kept"*). Silently
storing 2,000 of somebody's 2,400 characters is data loss dressed up as success.

## F. what I could not do, and why

- **Surfacing in `recall` and `ls`.** Both files are reserved (T10.7 is inside `recall.ts` and
  `calibration.ts` right now). The storage and the search function exist and are tested —
  `searchNotes()` returns bm25-ranked rows already stamped `kind: 'note'` — but nothing fuses
  them yet. Exact patches in §H1/§H2. **Today a note is invisible to `find`/`recall` rather than
  mislabelled in it**, which is the fail-safe direction.
- **The MCP tool.** `packages/mcp/**` is reserved. Definition in §H3.
- **The core barrel export.** `packages/core/src/index.ts` is reserved, so `note.ts` imports
  `notes.ts` by relative path with a comment saying why. Under vitest this is the same module
  (`vitest.config.ts` aliases `@potsherd/core` to `src/index.ts`); in the esbuild bundle it pulls
  in `notes.ts` and `threads.ts`, both of which import `Db` **as a type only** and hold no
  module-level state, so there is no second driver or connection cache. One line in §H4 makes it
  a normal import.
- **Author detection.** I cannot tell an agent typing `potsherd note` from a human typing it — a
  terminal is a terminal. `CLAUDECODE=1` in the environment would be a guess about the
  *environment*, not about who typed, and a guessed provenance on an assertion table is worse
  than none. So `author` defaults to `'unknown'` and is only ever what `--by` states. `via` is
  the half that *is* certain: `cli` from the terminal, `mcp` when the server calls in. **Item 8:
  nothing about a note is inferred.**
- **Notes on ghosts across an id change.** A note is filed against the thread id as derived *at
  write time*. `session_threads` is rebuilt whole on every `index`, so a re-derivation that
  merges two chains leaves an older note under the pre-merge thread id. It is not lost — both
  columns are stored, and `session_id` still resolves — but `threadNotes` on the merged chain
  will not return it. Fixing that means a re-derivation step that re-points notes, which is a
  write to an existing row, which I will not add without you asking. **Reported, not fixed.**

and one function, modelled on `bm25Cards`. A note is keyed by **thread**, so it is attributed to
the thread's head session, which is what the rest of `recall` treats as the session:

```ts
/**
 * bm25 over `notes_fts` — the assertion lane.
 *
 * Deliberately **not** joined to `sessions`: a note can be filed against a
 * ghost or against a chain whose head was swept, and a join would hide both.
 * The session filters are applied to the thread's head instead, via
 * `session_threads`.
 */
function bm25Notes(db: Db, match: string, filters: SearchFilters, depth: number): RawHit[] {
  const f = buildSessionFilters(filters);
  return (
    db
      .prepare(
        `SELECT n.session_id AS session_id, n.decided AS decided, n.open AS open,
                n.next_step AS next_step, n.written_at AS ts,
                bm25(notes_fts, 1.4, 1.0, 1.2) AS rank
           FROM notes_fts
           JOIN notes n    ON n.rowid = notes_fts.rowid
           JOIN sessions s ON s.id = n.session_id
          WHERE notes_fts MATCH ?
            ${f.sql}
          ORDER BY rank
          LIMIT ?`,
      )
      .all(match, ...f.params, depth) as {
      session_id: string; decided: string; open: string; next_step: string;
      ts: string; rank: number;
    }[]
  ).map((r) => ({
    key: `n:${r.session_id}:${r.ts}`,
    kind: 'note' as const,
    sessionId: r.session_id,
    ts: r.ts,
    userText: r.decided || r.next_step || r.open,
    assistantText: [r.open, r.next_step].filter(Boolean).join(' · '),
    isSidechain: false,
    raw: r.rank,
  }));
}
```

### H3 · `packages/mcp/**` — the fourth tool

`packages/mcp/src/tools/note.ts`:

```ts

import type { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';

import { addNote, threadNotes } from '../../../core/src/notes.js';
import { withIndex, type ServerContext } from '../context.js';
import { NOTE_DESCRIPTION } from '../descriptions.js';
import { guarded, jsonResult } from '../result.js';
import { THREAD_REF } from './shapes.js';
import { resolveThreadRef } from './thread.js';

export const noteInput = {
  thread: THREAD_REF,
  decided: z.string().max(2000).optional()
    .describe('what this thread settled. One sentence, in your own words'),
  open: z.string().max(2000).optional()
    .describe('what it left unresolved'),
  next: z.string().max(2000).optional()
    .describe('the single next step, concretely enough to act on'),
};

export type NoteArgs = z.infer<z.ZodObject<typeof noteInput>>;

export function runNoteTool(ctx: ServerContext, args: NoteArgs): Record<string, unknown> {
  return withIndex(ctx, (db) => {
    const thread = resolveThreadRef(db, args.thread, 'note');
    const written = addNote(db, {
      sessionId: thread.threadId,
      decided: args.decided ?? null,
      open: args.open ?? null,
      next: args.next ?? null,
      // Certain, not guessed: this code path IS the agent.
      author: 'agent',
      via: 'mcp',
    });

      lane: 'notes',
      appended: true,
      superseded: null,
      transcriptTouched: false,
      thread: written.thread,
      earlier: written.previous,
      wrote: { kind: 'note', citable: false, ...written.note },
      notes: threadNotes(db, written.thread.id).map((n) => ({ kind: 'note', citable: false, ...n })),
    };
  });
}

  server.registerTool(
    'potsherd_note',

      title: 'Leave the verdict on a thread',

      inputSchema: noteInput,
```
