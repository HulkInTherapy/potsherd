## d. the dating function: promoted and deleted

- **Promoted:** the expression `s.endedAt ?? s.startedAt` that lived inline in
  `graft.ts::collectSource`. It is now `threads.ts::sessionDate()` (with `sessionDay()` for the
  `YYYY-MM-DD` form the `source:` line carries). `graft.ts` imports it; **the inline copy is gone.**
  It was the only correct dating computation in the codebase, and it was correct for a reason worth
  writing down: the *head* of a forked transcript is inherited and the *tail* never is, so preferring
  the end was accidentally immune to the bug.
- **Deleted, in effect:** the *other* rule was not a function but a column. `sessions.started_at` was
  the timestamp of the first record in the file. `threads.ts::contentStartedAt()` /
  `redateFromContent()` replace it with the first exchange the session actually owns, at write time.
  That is why `find` prints the content date without knowing what a thread is: there is one column,
  and it is now true. No reader changed — including the reserved ones.

`renderShow` reads `s.startedAt`, `renderLs` and `browse.when()` read `endedAt ?? startedAt`,
`recall.fromSessionRow` reads both. All four now agree because the data agrees.

## e. the threshold, as a stopping rule

`OVERLAP_THRESHOLD = 0.75`, `MIN_SHARED_RECORDS = 10`, in `threads.ts`.

The measure is **containment**, `shared / min(|a|, |b|)`, not Jaccard: a resume copies the parent's
history whole, so the parent's record set becomes a near-subset of the child's, and Jaccard would
punish exactly the case this exists to catch — a child scores *worse* the more new work it did.

It is not an argmax, and the honest reason is that an argmax would be theatre. The distribution is
bimodal with nothing in between: chains at 0.9604 and 0.9881, every other pair at exactly 0.000. Any
value in (0, 0.96] gives the same answer on this corpus. 0.75 is where we **stop looking** — three
quarters of one file being a copy of another is where "one of these is a fork of the other" stops
being arguable — and it is far from both walls of the only gap there is.

`MIN_SHARED_RECORDS = 10` exists because containment over a tiny denominator is noise with a decimal
point on it. The smaller real chain clears it by a factor of nineteen.

**The test that fails when the constant moves** (`tests/threads.test.ts`, "the overlap threshold"):
a fixture pair at containment 0.80 must chain and a fixture pair at 0.70 must not, plus a direct
assertion `0.7 < OVERLAP_THRESHOLD ≤ 0.8`. Moving the constant in either direction fails the suite.

## f. declared metadata: verified, preferred, and not trusted alone

The ruling was to prefer Claude Code's own resume metadata. I checked what the records contain rather
than what any document says, and both halves of the answer matter.

**It exists.** Every record in a resumed transcript carries `sessionId` rewritten to the new
transcript and a *separate* `session_id` still naming the transcript the record was first written in.
On chain 1: 1,387 of 1,836 records name the parent. `promptId` does **not** survive the copy, which is
the mechanism behind the whole defect — the parser opens no exchange for a copied prompt, so the
derived session indexes as a stub while its parent keeps all 119 exchanges. **The dedup is right and
is untouched.**

**It over-matches badly on its own.** Sixteen declared pointers exist in this archive across twelve
sessions. Eight name a session that is not indexed at all. Of the eight that do, **six share zero
record ids with the session they name** — one declares 2,097 records inherited from a transcript that
contains 98 in total. The field is sticky across a `/clear`: it keeps naming the pre-clear session on
records written *after* it, so used alone it merges conversations with nothing in common. A method
built on it would have reported **10 chains** on this archive, and eight of them would be false.

So: **the declared pointer is preferred where the records corroborate it**, overlap is the fallback
for a fork the harness never pointed at, and every refusal is recorded in
`ThreadReport.refused` with which of the three reasons applied. Both real chains fired on
`via = 'declared'`; overlap alone would have found the same two and no others.

**Per harness.** Only claude is in `LINEAGE_HARNESSES`, and only because its record identity was
verified on real transcripts. The other six adapters get no chains and `ThreadReport.withoutLineage`
names them — not an empty result dressed up as a measurement, and not an invented one. The reference
machine has no codex/cursor/pi/gemini/opencode/copilot sessions, so nothing there could be verified.

## g. cold vs incremental

All three runs derived the identical four rows of `session_threads`, byte for byte:

| run | parsed | skipped | wall | chains |
|---|---:|---:|---:|---:|
| cold, fresh `--potsherd-dir` | 328 | 0 | 18.4 s warm / 39.0 s cold page cache | 2 |
| incremental over that index | 9 | 319 | 4.1 s | 2 |
| **upgrade in place** — a schema-9 database written by `origin/main`, reopened by this build | 328 | 0 | 38.9 s | 2 |

The third row is the one that needed the migration: `deriveThreads` reads *stored* record ids, so a
database that predates migration 11 has none, and an incremental pass would skip every transcript for
ever and derive from an empty table. Migration 11 clears `sync_state` and `sessions.source_mtime`
(migration 5's trick, for migration 5's reason), so the first index after upgrade re-reads once and
fills the evidence honestly.

`tests/threads.test.ts` pins the harder form as well: a parent indexed alone, then the resume
appearing weeks later, chains on an incremental pass that opened exactly one file.

**Cost.** The lineage pass is a second read of each changed non-sidechain claude transcript,
extracting only `uuid` and `session_id`. Measured: **+2.0 s on a 435 MB archive** (16.4 s → 18.4 s
warm), and 2.8 s standalone over all 79,531 records. `JSON.parse` costs 0.3 s more than a regex over
the raw line, which is not a price worth paying in guesswork, so it parses.

## h. `--since` / `--until`

`buildSessionFilters` reads `--until` as `started_at <= ?`. With `started_at` inherited from the fork
point, a session whose only content was written on 20 august claimed to have been alive on the 12th.

```
$ potsherd ls --project <p> --until 2026-08-15

  before: potsherd ls · <p> · until 16 aug · 5 sessions
            20 aug   …            ← the resume, whose first exchange is on the 20th
            20 aug   …            ← its parent
            12 jul   …
             9 jul   …
             9 jul   …

  after:  potsherd ls · <p> · until 16 aug · 4 sessions
            20 aug   …            ← the parent alone; "20 aug" is 19 aug 18:49Z in local time
            12 jul   …
             9 jul   …
             9 jul   …
```

**The ordering that changes:** a listing headed `until 16 aug` no longer contains a session whose
first exchange is on the 20th. The resume is out because its content starts on the 20th; the parent
stays because its content ran 12→19 august, and it keeps its own row rather than being folded into a
head this filter dropped.

That last clause is a defect I introduced and then fixed. The first version of `THREAD_ROLLUP` folded
every non-head link unconditionally, and `--until 15 aug` lost the whole chain: the 119-exchange link
was folded away as a member, and the link it was folded into failed the filter. The clause now
repeats the query's own filters inside its `EXISTS`, so a link is only folded into a head that is
actually on this screen — the same guarantee the sidechain rollup makes, tightened from "the head is
in the index" to "the head is in this result".
