# T10.10 — a retrieval eval set big enough to measure something

branch `work/T10.10` · fixture corpus only · gate, thresholds and weights untouched

---

## the short version

The 25-query set was widened to **60 recall queries and 6 confidence controls**.
Every gold label was verified against the built index. No query trips the
answer-overlap flag. `pnpm evals` **exits 1** and `pnpm evals --vector-weight 0`
**exits 1**, so the set can still fail.

The finding that matters is not the score. It is this: **widening the set did not
remove the coin flip, it moved it, and showed that one clause of the gate cannot
be resolved on this corpus at any set size.**

- On 60 queries, the recall@1 half of the §8.5 gate — the clause the amendment was
  written for — now **passes**: hybrid 27, bm25 25, vectors 22. But hybrid and
  bm25 disagree on only **4 of 60 queries**, McNemar p = 0.625, and the paired
  bootstrap puts P(the difference is really ≤ 0) at **0.226**. The clause passes
  and the pass means nothing.
- The verdict now turns on the *absolute bar* instead: `round(0.88 × 60) = 53` and
  hybrid scores **52**. The bootstrap 95% CI on that count is [46, 57] and
  P(hybrid@5 ≥ 53) is **0.445**. A one-query margin against a ±5-query
  uncertainty. The same disease, a different clause.
- The one clause that *is* decisive is hybrid ≥ both singles at recall@5: **+23**
  over bm25, 23 discordant queries to 0, p = 2.4 × 10⁻⁷.

I changed nothing to make any of that come out differently.

## (a) how many queries, by class

**60 recall queries + 6 controls.** The corpus is 46 live sessions, 12 ghosts, 6
subagent transcripts, 33 cards, 8 projects.

| `needs` (where the answer physically is) | n |
|---|---|
| `text` — the ordinary exchange body | 36 |
| `ghost` — deleted session, prompts only | 12 |
| `sidechain` — only in a subagent transcript | 6 |
| `card` — only in the card summary | 6 |

The 25-query set covered 5 of 6 sidechains and 5 of 12 ghosts. This one covers
**all 6 and all 12**.

| form (tagged at the head of each `note`) | n |
|---|---|
| a natural-language sentence | 57 |
| one-or-two distinctive words (`[keyword]`) | 10 (7 recall + 3 controls) |
| a cross-project question | 8 |
| a question about a decision | 6 |
| **an honest answer of "the corpus does not contain it"** | **3** |

The no-answer golds use the format's existing mechanism — `control: "no-match"`,
which carries no `expected_session_prefix` because there is no session to name and
is scored by the control block rather than folded into recall. No format was
invented. The three are `dark mode for the invoice pdf`, `rate limiting the
sitemap generator`, `bluetooth on the checkout page`; each is a conjunction of two
topics the corpus really has, describing a session it does not.

The form axis is carried in `note` rather than in a new field, because
`evals/queries.jsonl`'s format had to be kept exactly and a new key would have
changed what `evals/run.ts` parses.

### the noise estimate, and how it was made

Three estimators, computed from the per-query hit vectors in `pnpm evals --json`.
Full method in `evals/QUERY-SET.md` §6.

1. **Binomial sd of a single count**, `sqrt(n·p·(1−p))` — how much one number
   would move if the 60 queries had been a different 60 drawn the same way.
2. **McNemar on the paired difference** — the correct estimator for every clause
   of the gate, because the two modes are scored on the *same* queries, so shared
   difficulty cancels and only the discordant queries carry information.
3. **Paired bootstrap**, 20 000 resamples of the 60 queries with replacement,
   recomputing both counts and their difference each time.

**single-count noise**

| number | value | sd |
|---|---|---|
| hybrid recall@1 | 27/60 | 3.85 queries (6.4 pp) |
| bm25 recall@1 | 25/60 | 3.82 queries (6.4 pp) |
| hybrid recall@5 | 52/60 | 2.63 queries (4.4 pp) |
| bm25 recall@5 | 29/60 | 3.87 queries (6.5 pp) |
| vectors recall@5 | 51/60 | 2.77 queries (4.6 pp) |

For scale: on the old 25-query set the hybrid recall@1 count had sd 2.45 queries
(9.8 pp). Widening lowered the noise in percentage points and raised it in
queries, which is why the paired estimator below — not this table — is what a gate
clause should be read against.

**clause-by-clause noise (this is the answer)**

| gate clause | measured | discordant | McNemar p | bootstrap 95% CI | verdict |
|---|---|---|---|---|---|
| hybrid ≥ bm25 @5 | 52 vs 29 (**+23**) | 23 to 0 | 2.4 × 10⁻⁷ | [+16, +30] | **real** |
| hybrid > bm25 @1 | 27 vs 25 (**+2**) | 3 to 1 | 0.625 | [−2, +6] | **undecided** |
| hybrid @5 ≥ 53/60 | 52 vs bar 53 (**−1**) | — | — | count [46, 57] | **coin flip** |

P(true recall@1 difference ≤ 0) = **0.226**. P(hybrid@5 ≥ 53) = **0.445**.

**Why the recall@1 clause is undecidable here, and why more queries will not fix
it.** Hybrid and bm25 put the same session first on **56 of 60** queries. The
power of a paired comparison is set by the number of discordant pairs, not by `n`.
At the observed 3-to-1 split, 17 discordant pairs are needed before McNemar clears
p < 0.05; the observed discordance rate is 4/60 = 6.7%; that implies **about 255
queries (est.)**. The corpus's hard ceiling is 58 (see (g)). The recall@1 clause
therefore **cannot be resolved on this fixture at any set size it can support.**

With only four discordant queries, the reader is entitled to see all four:

```
hybrid-only  charged the customer twice because the client retried
hybrid-only  why the conversion chart said more finished than began
hybrid-only  stopping tab from wandering behind the overlay
bm25-only    stop counting the same event twice in the rollup
```

**The rule for the next person.** On this set, at recall@1 a difference of ±4
queries or less between two rankers is noise unless the discordant list is
one-sided; ±2 certainly is. At recall@5 a difference of 5 or more is real. The bar
clause carries ±5 queries of uncertainty and currently sits one query below its
threshold, so it will flip on a change that means nothing.

## (f) how gold labels were verified

Three checks, all against the built index rather than against the generator.

**(1) automated structural assertion over all 66 lines.** With `pnpm evals --keep`
to get an index, every query was asserted: the gold prefix resolves to a session
that exists; the `needs` label is *true of that session in the index* (a `ghost`
gold has a row in `ghosts`, a `card` gold a row in `cards`, a `sidechain` gold a
child session with `is_sidechain = 1`, a `text` gold rows in `exchanges`); the
answer-overlap is ≤ 0.6; and for every `card` gold the card overlap is **strictly
greater** than the body overlap. For each `no-match` control, no single session in
the index contains all of its content words. Result: `queries checked: 66,
PROBLEMS: 0`.

**(2) one `potsherd show` per gold, 58 of them.** All 58 resolve, none ambiguous,
none failed.

**(3) the runner's own overlap column**, on every run, which keeps (1) honest after
this document stops being read.

## (g) what I could not do, and why

**The corpus is exhausted at 58 queries, and the set is at the ceiling.** The
fixture holds 46 live sessions and 12 ghosts. The set has **58 distinct gold
prefixes — every session in the corpus is now the gold answer to exactly one
query**, with two sessions carrying two queries of different kinds (`a82ceb72`
text + sidechain; `4c07b9e3` a keyword and a sentence about the same memory, kept
deliberately as the controlled comparison between the two forms). A 61st honest
query would have to be a second question about a session that already has one, and
that is padding, not power. This is why the recall@1 clause cannot be rescued by
widening further: it needs ~255 queries (est.) and the corpus supports 58.

**Short queries are structurally near-impossible on this corpus.** A one-or-two
word query whose distinctive word appears in its answer's transcript —
`pgbouncer`, `conntrack`, `viewBox`, `inodes`, `backpressure`, `cursor
pagination`, `startupProbe` — lands at 0.5–1.0 overlap and trips the flag by
construction. A short query can only stay under the line when its distinctive word
lives **only on the card**, which is true of six sessions. Hence 7 short recall
queries rather than 20. That is a property of the fixture, not an omission; richer
cards would lift it.

**One no-answer control fails, and I left it red.** `bluetooth on the checkout
page` must return zero rows and returns two at `weak`:

```
d80a3f16  Funnel report double counted a step
a86656f1  Flaky end-to-end test on the checkout page
```

Neither has anything to do with bluetooth. This is the T10.1 failure mode arriving
from a direction T10.1's own control did not cover: `kubernetes ingress payment
service` spreads its words thinly and is withheld correctly, whereas here **one
half of the query matches one session's title almost verbatim** and carries the
pair over the floor on its own. The other two new controls return zero rows with 3
and 4 withheld. The defect is in the confidence floor in `packages/`, which T10.10
is not scoped to change, so it is **reported and not fixed**. It is also not
deleted: a control removed because it fails is not a control.

### two arguments about clauses I did not change

**The absolute bar does not survive a change of set.** `PHASE_3_GATE = 22/25` was
not chosen as a difficulty-independent standard; it was *22 out of the specific 25
queries phase 3 wrote*. `run.ts` applies it as a proportion, so on 60 queries it
becomes 53/60, and a proportion inherited from one exam is not a pass mark on
another. The measurement in (d) says any replacement floor needs to sit further
than ~5 queries from where the build actually scores, or it is a coin flip with a
rule attached. **I changed nothing.** Three previous phases considered changing
this gate to fit a result and the answer was no; this is the fourth and the answer
is still no. It is a decision for the gate's author.

**The recall@1 clause is unmeasurable on the fixture.** Not wrong — recall@1 is
the number a user experiences and the amendment's reasoning is sound. But this
corpus cannot supply the discordant queries needed to test it, so on the fixture
set that clause will pass or fail for reasons unrelated to the fusion. That, too,
is a decision for the gate's author, and again nothing was changed.

### two defects found outside scope, reported not fixed

1. **The briefing's corpus pointer is wrong.** T10.10 was told to read
   `scripts/make-demo-corpus.mjs` as "the generator for the corpus the set runs
   against". It is not. `make-demo-corpus.mjs` builds the **demo** corpus under
   `.tmp/demo-home/.claude` for the readme and `docs/screens/`. The eval set runs
   against `evals/fixture/claude`, generated by **`scripts/make-eval-corpus.mjs`**,
   which is what `evals/run.ts:buildFixtureIndex` reads. I read both; the set was
   written against the correct one. Worth correcting wherever that instruction came
   from, because a worker who read only the named file would have written 60
   queries about the wrong corpus.
2. **The confidence floor lets a near-verbatim title match carry an absent
   topic**, as above.
