## c. structural or statistical? — **structural**, and here is the proof

It is a **partition**, not a weight.

```ts
export const LANES: Readonly<Record<Lane, number>> = { evidence: 0, routing: 1 };

export function byLane<T extends { lane?: Lane; score: number }>(a: T, b: T): number {
  return (LANES[a.lane ?? 'evidence'] - LANES[b.lane ?? 'evidence']) || b.score - a.score;
}
```

`byLane` is the comparator for `result.sessions` and for `result.hits`. The
fused score is the **second** term of a JavaScript `||` chain: when the lanes
differ the first term is non-zero and the score is never evaluated. No value of
`WEIGHTS.cards_fts`, `WEIGHTS.vec_cards`, `k`, `RELAXED_PENALTY` or
`CORROBORATION` can reach the comparison, because the comparison it would have
to win is not run.

Proved twice, and neither proof is "the default weights come out right":

1. **The weight sweep.** Every ordering assertion in `tests/cards-lane.test.ts`
   runs twice — once at the shipped weights and once with `cards_fts` and
   `vec_cards` **multiplied by a thousand** (`1200` and `1500`). The card block
   goes from scoring `1.7x` the transcript block to scoring hundreds of times
   it, and its rank does not move.
2. **The constant moves and the tests fail.** Setting
   `LANES = { evidence: 0, routing: 0 }` — which collapses `byLane` to
   score-only, i.e. exactly v1.1.0 — fails three tests:

   ```
   × the constant that encodes the lane > is evidence 0, routing 1, and fails when either moves
   × the audit's failing case > ranks the card-only block below a transcript block that scores lower than it
   × the audit's failing case > puts every routing block below every evidence block, at any card weight
        Tests  3 failed | 14 passed (17)
   ```

**The one thing that is *not* structural, stated plainly.** A card *inside* a
block that already has transcript hits still contributes to that block's fused
score, so it can move that block's rank relative to another evidence block. It
cannot move its `coverage` or its `confidence`. That split was measured, not
assumed — see (f) — and it is held by
`CARDS_SCORE_EVIDENCE_BLOCKS = true`, whose docstring carries the numbers. The
strict version (a card contributes to no ordering anywhere) is one word away and
costs four points of recall@5.

Demoted, not silenced. `tests/cards-lane.test.ts` asserts the same thing against
`evals/fixture` and then asserts that the words really are absent from the
session's transcript, by querying `exchanges_fts` directly — so the test cannot
pass for the wrong reason.

The ceiling is `weak` rather than `none` for exactly this: `find` runs at a
`weak` floor, so a `none` ceiling would have deleted every card-only row from
the default screen and turned the demotion into a silencing.

Two smaller pieces of the same rule:

- The **routing lane has its own build budget.** The first cut stopped building
  blocks at `limit * 3` conversations; since `order` is now every evidence
  conversation followed by every routing one, a query that relaxes and turns up
  thirty mediocre transcript blocks would never have *built* the card block at
  all. Demotion would have become deletion silently.
- **One card per conversation** (`ROUTING_PER_SESSION = 1`). Two summaries of
  one conversation are not two pieces of evidence about anything.

## e. could a card-only hit reach `strong`? — **yes, and it did. fixed.**

Measured on the demo corpus at `54b7f85`, before the change:

```
$ potsherd find "tile pyramid" --json
[{"id":"38d7fad6","confidence":"strong","calibrated":0.85,"kinds":["card"]}]
```

`strong` on a hit whose only evidence is a summary. The arithmetic is not an
accident, it is inevitable: coverage is counted over the text the row can
*show*, and for a card that text is the summary — so a card that paraphrased
the user's question covers it perfectly and, at rank 1 of an uncorroborated
list, scores `1.0 x (0.6 + 0.25 x 1) = 0.85`. Corroborated by `vec_cards` it is
`1.0 x (0.6 + 0.25 + 0.15 x 0.5) = 0.925`. `STRONG_FLOOR` is `0.75`. Both clear
it comfortably.

**What I changed in `calibration.ts`:**

- `ROUTING_CEILING: Confidence = 'weak'` — the best label a row whose only
  evidence is a card may ever carry, named in the file that owns what `strong`
  *means* (*an agent may act on this without reading the rows*).
- `capConfidence(a, b)` — the `min` over the three-word ladder, mirroring
  `maxConfidence`.
- `RowEvidence.ceiling?: Confidence` — the generic mechanism. `recall()` owns
  the policy (which rows are disqualified); `calibration.ts` owns the meaning.
- `Calibrated.ceiling?: Confidence` — surfaced so `--json` says *why* a row
  reading `calibrated: 0.85` is labelled `weak`, instead of leaving a caller to
  conclude the two numbers disagree.
- `calibrate()` caps the **label** and deliberately **not** the score. A capped
  score would have stopped `coverage x (base + …)` reproducing, which is the
  one property that makes the module debuggable from `--explain` alone.

The same query, after:

```
$ potsherd find "tile pyramid" --json
[{"id":"38d7fad6","lane":"routing","citable":false,"confidence":"weak",
  "calibrated":0.85,"ceiling":"weak"}]
```

`ROUTING_CEILING = 'strong'` fails three tests, so the constant is pinned in
both directions.

I also stopped a **second** laundering path in `recall.ts`: an evidence block's
`calibration` used to be computed over the union of *all* its hits, cards
included. Coverage is the ceiling in `calibrate`, so a card's summary could lift
the confidence of a whole conversation. An evidence block is now calibrated over
its evidence hits and its title only; a routing block over its card, under the
ceiling.

## g. what I could not do, and what I found and did not fix

1. **`--no-cards` is not reachable from the command line yet.** The core option,
   the `runFind` forwarding and the tests are all in and green; the registration
   lives in `packages/cli/src/index.ts`, which is reserved. Exact lines in (i).
   The flag is off by default and does nothing until both halves land — and
   *both* is the operative word, per the mistake that already shipped once this
   phase.
2. **`potsherd_recall` still mints a citation for a card-only thread.**
   `packages/mcp/src/tools/recall.ts:groupThreads` mints one for every thread on
   the page. T10.6 already got the two harder halves right — `hitJson` carries
   `evidence: 'not-a-transcript'` for a card, and `windowsFrom` skips card hits
   so no window ever cites one — but a card-only *thread* is still handed a
   syntactically perfect, index-resolvable citation, which `verifySources` will
   keep. **This is the one place the acceptance criterion "cannot appear in
   `SOURCES`" is not yet enforced in code.** Lines in (i). `sources.ts` itself
   is the wrong place for the rule: it verifies against the index, and a
   card-only thread *is* in the index — the refusal has to happen where the
   citation is minted, which is `recall.ts`.
3. **`packages/mcp` does not typecheck, on `main` and on this branch.**
   `src/tools/recall.ts(19,8): error TS2724: '"./shapes.js"' has no exported
   member named 'Confidence'` — `shapes.ts` documents importing `Confidence`
   from the core barrel and then re-exports nothing. Pre-existing (verified by
   checking out `HEAD~1 -- packages/` and re-running), reserved, reported not
   fixed. `pnpm build` is unaffected because the mcp bundle is built with
   esbuild.
4. **A card title can still reach a block's coverage by the back door.**
   `fromSessionRow` prefers `cards.title` over `sessions.title` (T2.4, correct
   for naming), so `RecallSession.title` and `.displayTitle` may *be* the card's
   title — and an evidence block's calibration folds its title in. So a carded
   session can gain coverage from six words a model wrote. Narrow (a title, not
   a summary; and only for blocks that already have transcript evidence, which
   are capped by nothing) but real. Fixing it means carrying `cardTitle` down
   into `SessionMeta`, which `browse.ts` derives from — another worker's file
   this phase. Reported, not fixed.
5. **`title` hits are not in the routing lane.** A title is not evidence either,
   but it is not the artefact of a model call over the transcript and it has
   never been citable, so widening `ROUTING_KINDS` would be re-litigating a
   different finding under F6's name. `ROUTING_KINDS` is a `Set` precisely so
   this is a one-token decision when someone wants to make it.
6. **`vec_cards` is exercised by `evals` but not by `tests/cards-lane.test.ts`.**
   The test seeds cards through `writeCard` without an embedding, so the vector
   half of the card lane is empty there and the fixture stays deterministic and
   model-free. The lane is list-agnostic — it partitions on `hit.kind`, not on
   which list produced the hit — and the weight sweep multiplies `vec_cards` too,
   so the property is asserted for a list that has no rows in that fixture. The
   `evals` run is where `vec_cards` actually has rows.
7. **The eval set rewards the behaviour F6 forbids, and this is worth T10.10's
   attention.** Five of its twenty-five queries are `class: card`, graded on the
   answer being within the top 5 of one flat ranking. Under the restated Bet 02
   the right question for those five is *"is the thread reachable in the routing
   lane"*, not *"is the summary in the top five, above the transcripts"*. On the
   shipped configuration all five are still at hybrid `#1` — because those
   sessions have transcript hits too, so they are evidence blocks — so nothing
   is failing today. It will start mattering the moment a genuinely card-only
   answer joins the set.
